MCP (connecter des outils externes en sécurité)

Model Context Protocol

En vibe‑coding, on branche des outils MCP au hasard sans savoir qui les a approuvés ni ce qu'ils peuvent lire. Passer pro, c'est maîtriser les scopes (.mcp.json versionné), les approbations et les allowlists/denylists.

Test de niveau

Quel statut affiche un serveur MCP de portée projet non approuvé dans .mcp.json ?

✓ Exact. Jamais d'auto‑approbation silencieuse : claude mcp list affiche le statut d'approbation de chaque serveur configuré.
→ Vous maîtrisez déjà ce levier, passer au module suivant
✗ Pas tout à fait. C'est « Pending approval » : un serveur MCP de portée projet non approuvé ne se connecte jamais silencieusement.

Qui a vraiment approuvé cet outil MCP branché sur votre projet ?

Vous avez sans doute déjà branché un serveur MCP en collant une commande trouvée quelque part, sans trop savoir ce qu'il pouvait faire une fois connecté. Ça se lance, les outils apparaissent, et on avance, jusqu'au jour où on se demande : à quelles données ce truc a-t-il vraiment accès, et qui a validé qu'il pouvait s'y connecter ? Un serveur MCP (pour Model Context Protocol) n'est pas un simple script local : c'est une passerelle vers un outil ou un service externe, avec ses propres identifiants et ses propres droits. Comprendre comment Claude Code encadre cette passerelle, c'est la différence entre une configuration qui « marche chez vous » par hasard et une configuration qu'on peut partager, auditer et faire confiance en équipe.

Le mécanisme repose d'abord sur une histoire de portée, ou scope : un serveur MCP peut être déclaré en local (juste pour vous, sur ce projet), en user (partout où vous travaillez), ou en project. Ce dernier scope est le plus utile en équipe, car il vit dans un fichier .mcp.json que vous committez avec le reste du code : toute personne qui clone le dépôt récupère automatiquement la même liste de serveurs MCP, sans avoir à la reconfigurer à la main. Mais partager une configuration dans Git ne veut pas dire l'exécuter sans regarder, et c'est justement là que Claude Code place un garde-fou.

Que se passe-t-il, concrètement, la première fois que vous ouvrez un projet contenant un .mcp.json ajouté par quelqu'un d'autre ? Claude Code ne connecte jamais silencieusement un serveur de portée project tant qu'il n'a pas été approuvé : il reste affiché comme Pending approval (en attente d'approbation), un statut que vous pouvez aussi consulter à tout moment avec claude mcp list. Cette règle (jamais d'auto-approbation) protège contre un scénario simple mais réel : un fichier de configuration glissé dans un dépôt, qui brancherait discrètement un outil sur vos fichiers ou vos identifiants dès le premier lancement.

Une fois un serveur approuvé, vous gardez encore la main individuellement grâce aux listes allowedMcpServers et deniedMcpServers. Elles identifient un serveur par son nom, son URL ou sa commande (avec des jokers), y compris pour des serveurs déployés à l'échelle d'une entreprise. Le protocole encadre aussi la façon dont les données circulent avec le serveur : le transport HTTP streamable est aujourd'hui recommandé, tandis que l'ancien SSE reste supporté mais est explicitement marqué déprécié dans la documentation. Autrement dit, sécuriser un outil MCP, ce n'est pas seulement décider s'il a le droit de se connecter, mais aussi comment il le fait. Voici, en détail, ce que ça change concrètement.

Exercice pratique

Créez un .mcp.json à la racine avec un serveur MCP HTTP public, puis lancez claude. Observez l'invite « Pending approval », acceptez‑la, puis vérifiez avec claude mcp list. Bloquez ensuite ce même serveur pour vous via deniedMcpServers dans ~/.claude/settings.json.

Solution & vérification

Créer un .mcp.json à la racine place le serveur en portée project : c'est ce fichier, committé, qui permet de partager la configuration en équipe via Git, mais toute entrée non encore approuvée s'affiche « Pending approval » plutôt que de se connecter silencieusement (jamais d'auto-approbation). Une fois approuvé côté équipe, le blocage individuel passe par deniedMcpServers dans ~/.claude/settings.json, qui matche le serveur par serverName, serverUrl ou serverCommand :

{ "deniedMcpServers": [{"serverName": "nom-du-serveur"}] }
  • Au lancement de claude, le message exact « Pending approval » apparaît pour le serveur du .mcp.json avant toute tentative de connexion.
  • Après acceptation, claude mcp list affiche ce serveur avec un statut d'approbation passé à approuvé (au lieu de Pending).
  • Après avoir ajouté l'entrée deniedMcpServers et relancé claude, ce même serveur n'apparaît plus comme disponible/connecté pour vous (ses outils ne sont plus proposés), alors qu'il reste actif pour le reste de l'équipe.
