SDK, mode headless, CI/CD & IDE

Faire de Claude Code une brique d'infrastructure

Le vibe‑coding valide chaque action à l'instinct en mode interactif : ça ne passe pas à l'échelle. Le mode headless et le SDK transforment Claude Code en brique reproductible : scripts déterministes, garde‑fous explicites, sortie structurée exploitable en CI.

Test de niveau

Quel flag saute la découverte automatique de hooks, skills, sous‑agents, plugins, MCP et CLAUDE.md ?

✓ Exact. C'est le mode recommandé pour tout appel scripté ou SDK : comportement prévisible, sans configuration locale implicite.
→ Vous maîtrisez déjà ce levier, passer au module suivant
✗ Pas tout à fait. C'est --bare : il élimine toute découverte automatique de configuration locale pour un comportement scripté prévisible.

Et si personne n'était là pour cliquer sur « Oui » ?

En mode interactif, tout est simple : vous voyez ce que Claude Code s'apprête à faire, vous validez ou vous corrigez au fil de l'eau. Mais que se passe-t-il quand vous voulez brancher Claude Code sur un pipeline CI/CD (le système qui construit et teste votre code automatiquement à chaque envoi) qui tourne à 3h du matin, sans personne devant l'écran ? Ou quand vous voulez l'appeler depuis votre propre programme, comme une simple fonction ? Le mode interactif, avec ses invites de confirmation et sa configuration locale implicite, n'a alors plus de sens : il faut un comportement qui reste identique à chaque exécution, sans surprise et sans dépendre de ce qui traîne sur votre machine.

C'est précisément le rôle du mode headless (sans interface, piloté uniquement par la ligne de commande) et du flag --bare. --bare fait table rase : il saute toute découverte automatique de hooks, skills, sous-agents, plugins, serveurs MCP, mémoire et fichier CLAUDE.md. Résultat : seul ce que vous passez explicitement sur la ligne de commande détermine le comportement de la session, ce qui la rend reproductible d'une machine à l'autre. Combiné à --permission-prompts none, qui transforme automatiquement en refus toute action qui aurait normalement déclenché une invite de confirmation, vous obtenez un script qui ne reste jamais bloqué à attendre une réponse humaine qui ne viendra pas. Le SDK, aujourd'hui renommé Claude Agent SDK, formalise la même logique côté code : au lieu de taper une commande, votre programme pilote directement une session Claude Code.

Mais un script sans supervision doit aussi savoir se protéger tout seul, à sa place. Le callback canUseTool du SDK illustre bien ce souci de couches : il n'est appelé que si rien avant lui (un hook PreToolUse, une règle allow/deny/ask, le mode de permission) n'a déjà tranché, ce qui vous laisse ajouter une validation métier sur mesure sans dupliquer ce qui existe déjà. Même logique de prudence côté résilience : le mécanisme fallbackModel bascule automatiquement sur un modèle de secours en cas de surcharge ou d'erreur serveur, mais jamais pour une erreur d'authentification, de facturation ou de rate-limit. Changer de modèle ne réglerait rien à ces problèmes-là : mieux vaut que le job échoue clairement plutôt qu'il masque un vrai incident. Quant à maxBudgetUsd, il plafonne la dépense d'une exécution automatisée : personne ne surveille le compteur en direct, c'est donc au paramètre lui-même de couper avant que la facture ne dérape.

Reste un dernier problème : comment un pipeline sait-il, sans humain pour lire l'écran, que tout s'est bien passé ? En produisant une sortie structurée plutôt qu'un texte à interpréter à l'œil. En --output-format stream-json, le message system/init expose par exemple un champ plugin_errors qui liste les erreurs de chargement de plugin (absent s'il n'y en a aucune), ce qui donne une porte de validation simple à écrire dans un script CI. Côté travail au clavier plutôt qu'en pipeline, le même CLI se retrouve intégré dans l'extension VS Code (panneau latéral, diffs inline, mentions @ liées à la sélection), et /statusline vous garde informé en direct du modèle, du coût et du contexte utilisés. Voici, en détail, ce que ça change concrètement.

Exercice pratique

Écrivez la commande suivante :

claude --bare -p "Résume les 3 derniers commits" --allowedTools "Bash(git log *)" --permission-mode auto --permission-prompts none --output-format json

Inspectez la sortie avec jq pour extraire .result et .total_cost_usd.

Solution & vérification

La commande fonctionne parce que --bare élimine toute découverte automatique de hooks, skills, sous-agents, plugins, MCP, mémoire et CLAUDE.md : seul ce qui est passé explicitement sur la ligne de commande (ici --allowedTools "Bash(git log *)") détermine le comportement, ce qui rend l'appel reproductible pour un script. Combiné à --permission-prompts none, qui transforme automatiquement en refus toute action qui aurait normalement déclenché une invite de confirmation, le job reste non interactif de bout en bout : toute commande hors du périmètre git log est rejetée sans attendre de réponse humaine. --output-format json produit ensuite un objet JSON unique dont jq extrait .result (le résumé) et .total_cost_usd (le coût de l'appel).

  • La commande se termine avec un code de sortie 0 et affiche un unique objet JSON sur stdout (pas plusieurs lignes, puisque le format n'est pas stream-json).
  • jq -r '.result' renvoie un texte non vide résumant bien les 3 derniers commits, et jq '.total_cost_usd' renvoie un nombre décimal positif (jamais null).
  • Aucune invite de confirmation n'apparaît pendant l'exécution ; si une commande hors du périmètre Bash(git log *) avait été tentée, elle aurait été refusée automatiquement au lieu de bloquer le terminal en attente d'une validation.
