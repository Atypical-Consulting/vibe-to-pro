MCP (Connecting External Tools Securely)

Model Context Protocol

In vibe-coding, you plug in MCP tools at random without knowing who approved them or what they can read. Going pro means mastering scopes (versioned .mcp.json), approvals, and allowlists/denylists.

Level check

What status does an unapproved project-scoped MCP server show in .mcp.json ?

✓ Correct. Never silent auto-approval : claude mcp list shows the approval status of every configured server.
→ You already know this lever, skip to the next module
✗ Not quite. It's "Pending approval" : an unapproved project-scoped MCP server never connects silently.

Who actually approved that MCP tool plugged into your project ?

You've probably already plugged in an MCP server by pasting a command found somewhere, without really knowing what it could do once connected. It starts up, the tools appear, and you move on, until the day you wonder : what data does this thing actually have access to, and who confirmed it was allowed to connect ? An MCP server (for Model Context Protocol) isn't just a local script : it's a gateway to an external tool or service, with its own credentials and its own permissions. Understanding how Claude Code governs that gateway is the difference between a setup that happens to "work on your machine" by accident and one a team can share, audit, and trust.

The mechanism starts with a matter of scope : an MCP server can be declared as local (just for you, on this project), as user (everywhere you work), or as project. That last scope is the most useful for teams, since it lives in a .mcp.json file you commit along with the rest of the code : anyone who clones the repo automatically gets the same list of MCP servers, with no manual reconfiguration needed. But sharing a configuration in Git doesn't mean running it without a look, and that's exactly where Claude Code puts up a guardrail.

What actually happens the first time you open a project containing a .mcp.json someone else added ? Claude Code never silently connects a project-scoped server until it has been approved : it stays shown as Pending approval, a status you can also check at any time with claude mcp list. This rule (never auto-approve) guards against a simple but real scenario : a configuration file slipped into a repo that would quietly wire a tool into your files or your credentials the first time it launches.

Once a server is approved, you still keep individual control through the allowedMcpServers and deniedMcpServers lists. They identify a server by its name, URL, or command (with wildcards), including for servers deployed company-wide. The protocol also governs how data flows with the server : the HTTP streamable transport is now recommended, while the older SSE is still supported but explicitly marked deprecated in the documentation. In other words, securing an MCP tool isn't just about deciding whether it's allowed to connect, but also how it does so. Here's exactly what that changes in practice.

Hands-on exercise

Create a .mcp.json at the root with a public HTTP MCP server, then launch claude. Watch for the "Pending approval" prompt, accept it, then check with claude mcp list. Then block that same server for yourself via deniedMcpServers in ~/.claude/settings.json.

Solution & verification

Creating a .mcp.json at the root places the server at project scope: it's this committed file that lets the team share the configuration via Git, but any entry not yet approved shows "Pending approval" rather than connecting silently (never auto-approved). Once approved on the team's side, blocking it for yourself individually goes through deniedMcpServers in ~/.claude/settings.json, which matches the server by serverName, serverUrl, or serverCommand:

{ "deniedMcpServers": [{"serverName": "nom-du-serveur"}] }
  • When claude launches, the exact message "Pending approval" appears for the .mcp.json server before any connection attempt.
  • After accepting, claude mcp list shows this server with its approval status now approved (instead of Pending).
  • After adding the deniedMcpServers entry and relaunching claude, that same server no longer appears available/connected for you (its tools are no longer offered), while it remains active for the rest of the team.
