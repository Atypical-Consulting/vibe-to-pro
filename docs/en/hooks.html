Hooks: automating without relying on the model

Deterministic rules, not hopes

In vibe-coding, you leave the model to decide on its own when to format, test, or ask for confirmation, and it sometimes forgets. Hooks turn these habits into rules that always run at the right moment, scriptable and shareable across a team.

Level check

✓ Correct. A failing typecheck can thus be fixed automatically by Claude, instead of interrupting the session.
→ You already know this lever, skip to the next module
✗ Not quite. It returns the block reason to Claude as a tool result, which lets it fix the issue and continue instead of stopping.

What if best practices just ran on their own, without you having to ask for them every time?

In vibe-coding, we've all lived through this: you ask Claude to run the tests before committing, or to format the code properly. Nine times out of ten it does. Then one day it forgets, in a hurry to answer something else. Nothing abnormal about that: at every step, the model decides for itself what to do, and a decision, even a good one in the vast majority of cases, remains a decision, not a guarantee. A hook changes the game completely: it's a rule you write once, and it runs automatically every time a specific event occurs in the session, whether the model thinks of it or not.

Concretely, how does it work? A hook attaches to an event in the Claude Code lifecycle (just before a tool runs, just after, before a context compaction that summarizes the conversation to free up space, and many others) and triggers an action you define at that exact moment: running a local script (type: "command"), calling an already-installed MCP tool directly by interpolating the event's fields (type: "mcp_tool"), or sending the event's JSON as a POST to an external service and waiting for its response (type: "http"). You can even target very precisely when the hook fires, thanks to an if field that reuses the permission-rule syntax, for example reacting only to git commands with something like Bash(git *). The hook doesn't ask the model anything: it just runs, period, which makes it a deterministic safety net rather than a hope.

But a hook isn't necessarily a barrier that stops everything cold. That's where it gets interesting: on a PostToolUse hook (the one that fires right after a tool has been used), the continueOnBlock: true option lets you return the reason for a block to Claude as a plain tool result, instead of abruptly interrupting the turn. A failing typecheck, for example, can thus be fixed automatically by Claude on the spot, without you having to restart anything yourself. At the other end of the session, a PreCompact hook can outright prevent a compaction from happening (by returning exit code 2), giving you time to archive what matters before the history gets summarized.

And because these rules can live in a config file shared by the whole team, or even be scoped to the lifecycle of a particular skill or agent via its frontmatter, everyone works with the same guardrails, without having to repeat the same instructions every session. Here, in detail, is what that changes in practice.

Quick quiz

According to the hooks documentation, which event fires right before a context compaction and can block it with exit code 2?

✓ Correct. PreCompact fires right before a compaction and can block it (exit code 2). PostCompact, on the other hand, fires only right after, which is useful for example for archiving important information before it gets compacted.
✗ Not quite. It's PreCompact: it steps in before the compaction and can block it with exit code 2. PostCompact fires after the fact, once the compaction has already happened, so too late to prevent it.

Hands-on exercise

Create a PreToolUse hook on Bash with if: "Bash(rm *)" that blocks (exit code 2) any rm command. Add a PostToolUse hook on Edit|Write with continueOnBlock: true that runs a linter and returns the error to Claude instead of stopping the turn. Inspect /hooks to see the provenance of each active hook.

Solution & verification

The first hook relies on the if field, which accepts the permission-rule syntax (for example Bash(git *)) to target a subcommand precisely. With if: "Bash(rm *)", the PreToolUse hook only fires on rm commands, and a script that exits with code 2 blocks the tool call. The second hook uses the continueOnBlock: true option on PostToolUse, which returns the block reason to Claude as a tool result instead of stopping the turn. A failing linter can thus be fixed automatically by Claude rather than interrupting the session. The final expected setup is therefore two entries in the hooks configuration: one on PreToolUse (matcher Bash, if: "Bash(rm *)", command that exits with code 2) and one on PostToolUse (matcher Edit|Write, continueOnBlock: true, command that runs the linter).

  • An rm command attempted by Claude is immediately rejected: the Bash tool doesn't run, and the error message returned by the hook (exit code 2) shows up as a tool result in the conversation.
  • After a change via Edit or Write that breaks the linter, the turn doesn't stop: the linter's error shows up as a tool result and Claude proposes a fix in the next message, instead of the session being interrupted.
  • The /hooks command correctly lists both hooks as active, with their provenance (the settings file where they're declared) and their respective matchers: Bash for the PreToolUse hook, Edit|Write for the PostToolUse hook.
