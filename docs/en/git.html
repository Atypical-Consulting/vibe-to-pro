Git, Worktrees & PR Automation

Working in parallel without collisions

Vibe-coding stops the moment code touches a shared repository: without worktrees or Git discipline, you overwrite other people's work or push unreviewed commits. Worktrees and PR automation let multiple agents run in parallel without collisions, leaving a clean trail.

Multiple agents, one repository: how do you avoid the pile-up?

You've probably already run Claude Code on a task, then opened a second window to have it fix something else while the first one was still running. And that's where things jammed: both sessions were modifying the same files on the same branch, and one eventually overwrote the other's work. That's not a bug, it's the logical consequence of a classic Git repository: a single working copy on disk, so only one agent at a time can touch it safely. So how do you run multiple agents in parallel on the same project, without playing musical chairs with branches?

The answer lies in a Git tool that's already there but often overlooked: the worktree. A worktree is a second working copy of the same repository, placed in a different folder, but sharing the same Git history: it's not a full clone, just a full-fledged branch you can modify without touching the main branch. Claude Code builds directly on this: the --worktree flag (or -w) creates this isolated folder under .claude/worktrees/<name>/, on a new branch named worktree-<name>, so an agent running inside it simply cannot overwrite what another agent is doing elsewhere. One question remains: where does this new work start from? By default, it starts from origin/<default branch> (a clean, up-to-date base), but if you already have unpushed local work you want to continue, you need to explicitly enable the option that starts from your local HEAD instead.

The second friction point of vibe-coding is the end of the task: once the code is written, you still have to commit, push, and open a pull request (a request to merge into the main branch, usually reviewed before being accepted). And that's exactly where a step gets skipped, or where you push directly to the main branch out of habit. Claude Code automates this mechanic: an agent working in the background inside a worktree commits and pushes its work before finishing, and only opens a draft pull request when the task warrants it, while respecting the Git instructions you've left in your CLAUDE.md. But automating doesn't mean letting everything happen unsupervised: in this commit, push, and pull request workflow, flags that could cause hard-to-undo damage (a forced push, an amended commit, a bypassed verification hook) are no longer run automatically, they now ask for explicit confirmation. In other words, automation removes the repetitive chore, not your final say on risky actions.

One last detail changes a lot day to day: all worktrees of the same repository share the same configuration (CLAUDE.md, permission settings, custom agents, skills, automatic memory), so there's no need to duplicate everything for each new parallel work stream. And to keep an overview without reopening GitHub every time, the status of the pull request tied to your current branch shows up as a simple colored dot in the interface. Here, in detail, is what that actually changes.

The --worktree flag (or -w) creates an isolated worktree under .claude/worktrees/<name>/, on a new branch worktree-<name>.

How to
claude --worktree feature-auth. Also add .claude/worktrees/ to your .gitignore.
code.claude.com/docs/en/worktrees
v2.1.133Confirmed

worktree.baseRef defaults to "fresh" (starts from origin/<default branch>) or "head" (starts from your local HEAD, including unpushed commits).

How to
{ "worktree": { "baseRef": "head" } } if you want every new worktree to start from your current local work.

Hands-on exercise

Run the following command to start an isolated session:

claude --worktree essai-pro

Modify a file, then run /code-review high --fix before committing, and finally /commit-push-pr. Check that a git push --force would not be auto-approved, and add worktree.baseRef: "head" to .claude/settings.json.

Solution & verification

claude --worktree essai-pro creates an isolated worktree under .claude/worktrees/essai-pro/, on a new branch worktree-essai-pro, which lets you modify a file without touching the current working branch. Once the file is committed, /commit-push-pr pushes the work and opens the PR. Since v2.1.229, it no longer runs silently for a dangerous flag: a git push --force asks for confirmation again instead of being auto-approved. For this worktree (and future ones) to start from the local HEAD, including unpushed commits, rather than from origin/<default branch>, you need to explicitly add the following configuration to .claude/settings.json:

{
  "worktree": { "baseRef": "head" }
}

This is the final setting expected by the exercise.

  • The directory .claude/worktrees/essai-pro/ exists and, inside it, git branch --show-current returns worktree-essai-pro.
  • When attempting a git push --force in this worktree via /commit-push-pr, an explicit confirmation prompt appears instead of the push running directly.
  • .claude/settings.json contains the key "worktree": { "baseRef": "head" } after the edit, and a new worktree created afterward has the same head commit as the current local branch (not the one from origin/<default branch>).
