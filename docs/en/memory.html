Memory: CLAUDE.md and automatic memory

Stop re-explaining everything every session

In vibe-coding, every session starts from zero : you repeat the same conventions, the same corrections. Mastering CLAUDE.md and automatic memory turns this volatile context into versioned configuration, shared across the team and auditable via /context.

Level check

How many types of notes does Claude Code's auto-memory record ?

✓ Correct. 4 types : user (preferences), feedback (confirmed corrections), project (project context that can't be inferred from the code), reference (where to find external information).
→ You already know this lever, skip to the next module
✗ Not quite. The answer is 4 : user, feedback, project, reference.

Why do you keep repeating the same instructions to Claude ?

You've probably already lived through this : you open a new session, and you have to explain everything again : which package manager to use, your team's naming convention, that trap in the legacy code you discovered last week. None of it is retained : every session starts with an empty context, as if Claude had never learned anything about your project. It's annoying, but above all it's a matter of method : what gets said out loud, session after session, needs to become written, versioned configuration, shared with the team and auditable, rather than lost in a conversation's history.

The first tool for this is the CLAUDE.md file at the project root : a permanent memo that Claude re-reads at every startup. You can even have it point to other files through an import syntax (@path/to/file.md), with a maximum depth of 4 hops to avoid endless import chains ; and if you instead want to prevent a path from being loaded automatically, just wrap it in backticks (`@README`). One small but revealing practical detail about the system's logic : you can also drop HTML comments into this file to leave notes for the humans who will read it. They're stripped out before being injected into the session's context, so they cost no tokens at all, while staying visible if someone opens the file directly.

But what happens when you correct Claude mid-task, rather than writing a rule ahead of time in CLAUDE.md ? That's where automatic memory comes in, enabled by default : it captures what happens during a session as notes sorted into 4 categories : your preferences (user), corrections you've confirmed (feedback), project-specific context that can't be inferred from the code (project), and pointers to external information (reference). Just say “remember that…” in natural language to trigger a save ; these notes live by default in a per-project folder that you can relocate via the autoMemoryDirectory setting, and you can turn off the whole mechanism via /memory or the CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 variable if you'd rather keep everything manual.

Why bother with this rather than letting the context rebuild itself every time ? Because a memory that keeps accumulating without ever being cleaned up quickly becomes just as cumbersome as no memory at all : a CLAUDE.md that keeps growing with information Claude could deduce from the code anyway. That's why /doctor can do the sorting for you : it spots what's redundant with the code, keeps the traps and non-standard conventions, proposes migrating the rest to skills or nested CLAUDE.md files, and applies nothing without your explicit confirmation. This accumulated memory doesn't just benefit you, either : /team-onboarding draws on it to generate an onboarding guide for a new teammate. Here, in detail, is what that changes in practice.

Quick quiz

How do you prevent an @path/to/file.md path from being automatically imported into CLAUDE.md?

✓ Correct. Correct. Wrapping a path in backticks (@README) prevents it from being automatically imported; without backticks, an @path/to/file.md path is indeed imported, with a maximum depth of 4 hops.
✗ Not quite. Not quite. It's the use of backticks around the path (@README) that blocks the import : HTML comments and import depth don't play that role.
Quick quiz

What happens to block HTML comments (<!-- … -->) present in a CLAUDE.md file when it's loaded into context?

✗ Not quite. Not quite. These comments aren't injected into context : they're stripped out before loading, while remaining visible if you open the CLAUDE.md file directly.
Hands-on exercise

Run /init to generate a basic CLAUDE.md, add a specific rule (“use pnpm, never npm”), then deliberately correct Claude on a preference during a task. Check with /memory that the correction was recorded in auto-memory, confirm the loading with /context, then run /doctor to see whether it proposes trimming your CLAUDE.md.

Solution & verification

The correction made mid-task about the pnpm preference is captured as a note of type feedback, one of the 4 types that auto-memory records (along with user, project and reference) to track confirmed corrections. It's this note that /memory should show, and that /context should list among the sources loaded in the session.

The final step through /doctor relies on the fact that it proposes deduplicating CLAUDE.md against the code, while keeping traps and non-standard conventions like the pnpm rule. It migrates the rest to skills or nested CLAUDE.md files, but only after your explicit confirmation, never silently.

  • /memory shows a new feedback-type entry corresponding to the pnpm correction, distinct from the user/project/reference notes already present.
  • /context lists a file under ~/.claude/projects/<project>/memory/ among the loaded sources, with its size in tokens counted in the displayed total.
  • /doctor first presents its findings on CLAUDE.md (what it proposes to remove because it's inferable from the code, what it keeps as a non-standard trap) and waits for confirmation before making any changes. No rewriting of the file should happen without this step.
