Plugins & marketplaces

Tooling the whole team, not just yourself

In vibe-coding, you install a random plugin you found and cross your fingers. Done properly, plugins and marketplaces give you reproducibility (version pinned by SHA), security (secrets never injected into a shell), and governance (explicit activation, visible token cost).

✓ Correct. Explicit activation is required even once the plugin is installed : it's a safeguard against silent activation.
→ You already know this lever, skip to the next module

You find a plugin on GitHub, you install it… and then what ?

A plugin is tempting : someone wrote it, you install it, and Claude Code suddenly knows how to do one more thing. In vibe-coding, that's often all anyone asks for. It works, so you move on. But a plugin is more than just an extra command : it can bring agents, hooks (scripts that fire automatically at certain moments), and even whole MCP or LSP servers (LSP stands for Language Server Protocol, the protocol that gives an editor a fine-grained understanding of a programming language), all packaged and distributed through a marketplace, a kind of shared catalog. And that's where it gets interesting for a team : by declaring that marketplace once in .claude/settings.json via extraKnownMarketplaces, everyone gets access without reinstalling anything on their own side.

But installing a plugin doesn't mean activating it, and that's a deliberate design choice. If its author set defaultEnabled: false in plugin.json, the plugin stays inert until you run claude plugin enable <name> yourself. Why this seemingly redundant step ? Because a plugin that activated itself on install would act on your project before you'd even decided to trust it. And before taking that step, you can query claude plugin details <name> : the command lists what the plugin carries and projects the token cost it will add to each session. That way you know what you're activating before you activate it, not after.

One classic problem remains : a plugin pointing at a GitHub branch can change under your feet, since a commit pushed next week isn't the one you tested today. That's why marketplace.json can pin a sha, a full git commit, like a frozen snapshot rather than a stream that keeps moving. Same logic when the plugin isn't even on git : a source of type archive installs a zip directly over HTTPS, with no git or npm, also with an optional SHA-256 hash to guarantee the content received is exactly what was expected. The result : what you tested is, down to the commit, what will run on your teammate's machine or in CI.

There's still the question of trust around configuration and security. Could a cloned repo quietly slip its own plugin settings into your session ? No : pluginConfigs is no longer read from project settings, only your user settings, --settings, or settings managed by your organization count. It's the /plugin command that writes them, into your own ~/.claude/settings.json. The same caution applies to a plugin's hooks : the ${user_config.*} substitution in shell form is blocked, because it would open an injection flaw if a configuration value contained malicious code ; you have to go through the exec form or read the $CLAUDE_PLUGIN_OPTION_<KEY> environment variable. Here, in detail, is what that changes in practice.

Hands-on exercise

Run the following command :

claude plugin init mon-plugin --with skills hooks

Add "defaultEnabled": false to the generated plugin.json, then verify that the following command is required to activate it :

claude plugin enable mon-plugin

Finally, run this command to see its projected token cost per session :

claude plugin details mon-plugin
Solution & verification

The plugin.json generated by claude plugin init doesn't activate anything on its own. As soon as you add "defaultEnabled": false to it, the plugin reference requires explicit activation before the plugin becomes active, even once installed. That's exactly why claude plugin enable mon-plugin becomes a mandatory step, not an optional one. Once the plugin is activated, claude plugin details mon-plugin lists its declared components (here the skills and hooks requested via --with skills hooks) and projects their token cost per session before you even have to use them, which lets you judge its footprint without running it blind.

  • Before claude plugin enable, a plugin command/skill invoked in the session fails or stays invisible, and claude plugin list (or /plugin in the REPL) shows mon-plugin with a disabled status.
  • claude plugin enable mon-plugin exits with status code 0 and moves mon-plugin to active status in claude plugin list.
  • claude plugin details mon-plugin displays a numeric estimate of the token cost per session (a numerical value), in addition to the list of declared skills and hooks, not just the component names.
