Subagents, delegate and parallelize

The Agent tool (formerly Task)

Vibe-coding is a single thread where everything gets mixed together: research, writing, tests, context exploding. Subagents isolate each task (separate context, restricted tools, sometimes a dedicated worktree) and let you consciously choose which model does what.

What if you could delegate without losing the thread?

You know that moment when a Claude Code session goes off in every direction: you have it search for a bug, then write a fix, then run the tests, then review a completely different file. After a while, the context (everything the model "remembers" from the conversation) gets so loaded that responses become less precise. This is the classic symptom of vibe-coding: a single conversation thread trying to carry everything at once. The solution isn't to do everything faster in that same thread, but to break it up: hand each task to a separate subagent, with its own context, that doesn't come pollute yours.

Concretely, this delegation mechanism relies on a tool that Claude Code calls Agent (originally named Task). By default, a subagent inherits all available tools (including file writing and running Bash commands), unless you explicitly restrict it with tools: or disallowedTools: in its frontmatter (the configuration header at the top of the file that defines the agent). This is what lets you create, for example, a strictly read-only code review agent: it technically can't break anything, even if it tries. You can push isolation even further with isolation: worktree, which has the subagent work in a separate git copy, branched from your default branch and automatically deleted if it contains no changes. That way you can experiment without ever touching your main repository.

But why stop at one subagent at a time? That's where parallelization comes in. /subtask launches a subagent that stays attached to your current session, visible in the task list; /fork, on the other hand, duplicates the entire conversation into a new, fully independent background session, handy for testing a risky approach without blocking your work. Forking is active by default as soon as you're in an interactive session. To keep an escalation of delegations from spiraling out of control, two safeguards exist: a cap of 20 subagents running in parallel (adjustable via the CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS environment variable, with no total cap across a whole session), and a nesting depth limited to 3 levels. Beyond that, the Agent tool disappears for every subagent except forks, to stop a subagent from endlessly spawning more subagents.

One question remains: which model runs each subagent? You're not obligated to hand everything to the most powerful (and most expensive) model. The resolution order goes from the parameter passed at invocation, to the agent frontmatter's model: field (which can also simply say inherit to pick up the conversation's model), to the CLAUDE_CODE_SUBAGENT_MODEL variable, down to the main conversation's model as a last resort: this lets you consciously assign a lightweight model to a simple task, and save the horsepower for what deserves it. A memory: field even lets you give a subagent persistent memory from one run to the next, at the scope of the user, the project (the recommended scope, since it's versionable with the code), or the local machine. And to create one of these subagents, you no longer need a dedicated assistant: just ask Claude in natural language, or edit a file directly in .claude/agents/. Here, in detail, is what that changes in practice.

Hands-on exercise

Ask Claude to create a read-only code-reviewer subagent (Read, Grep, Glob), model haiku. Launch /subtask with this agent and watch it run in the background via /tasks. Then add isolation: worktree so it works in an isolated git copy, and finally block it with a permissions.deny: ["Agent(code-reviewer)"] rule.

Solution & verification

Restricting it to the Read, Grep, Glob tools works because a subagent receives all available tools by default, writing and Bash included, unless explicitly restricted via the frontmatter's tools: or disallowedTools: field. It's this same tools: Read, Grep, Glob declaration that makes it strictly read-only. Adding isolation: worktree next makes it run in an isolated git copy, branched from the default branch and automatically cleaned up if no changes were made, without touching the main repository. The exercise ends with a permission rule explicitly blocking this subagent, of the form permissions.deny: ["Agent(code-reviewer)"] in the settings.

  • In /tasks, the code-reviewer subagent's entry goes from "Working" to "Completed" without any call to Edit, Write, or Bash appearing in its tool transcript (only Read, Grep, Glob show up there).
  • Once isolation: worktree is added, a new worktree appears for the duration of the run (visible via git worktree list) and then disappears on its own at the end if no file was modified.
  • After adding the permissions.deny: ["Agent(code-reviewer)"] rule, any new attempt to invoke this specific subagent is explicitly denied with a blocked-permission message, instead of running as it did before.
