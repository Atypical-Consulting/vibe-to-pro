Epilogue: the practitioner's checklist & sources

Twelve levers, one goal: never have to hope again. Here's the checklist that sums up this course. Check it before calling any Claude Code project "production ready."

Hands-on exercise

Go back to your training repo from module 01 and combine three levers you've already practiced into one coherent setup: (1) the active sandbox with a sandbox.credentials.files rule (Control & Security module), (2) a PreToolUse hook that blocks rm without confirmation (Hooks module), and (3) a session opened in an isolated claude --worktree (Git & Worktrees module). Start a session in that worktree and verify all three protections stay active at the same time: that's exactly the .claude/ setup the checklist below describes, not three settings tested in isolation one by one.

The practitioner checklist

  • Bash sandboxing and network rules are active on every project touching secrets or production.
  • .claude/settings.json (permissions, hooks) is version-controlled and reviewed like code.
  • CLAUDE.md documents the non-standard pitfalls and conventions, not what Claude can already infer from the code.
  • Repeated tasks live in versioned skills, not in the memory of whoever types the prompt.
  • Risky tasks go through plan mode before any execution.
  • Subagents have an explicit tool scope (tools:/disallowedTools:), not full access by default.
  • Critical checks (lint, tests, secrets) are hooks, not hopes.
  • Every external MCP server is reviewed before approval, with a team allowlist.
  • /rewind and worktrees are the reflex before any risky experiment on shared code.
  • Multi-agent workflows have a deliberate workflowSizeGuideline, not "let it run and see."
  • Installed plugins are pinned by SHA and their token cost is known (claude plugin details).
  • CI integrations use --bare, --output-format json output, and explicit permissions, never a --dangerously-skip-permissions in a shared pipeline.

Synthesis quiz

Quick quiz · controle

What exactly does the --restricted flag do, compared to a session in bypass mode?

✓ Correct. Correct. --restricted removes the command-execution tools and WebFetch, confines file tools to the working directory, and refuses bypass mode; this choice cannot be undone mid-session. Reserve it for opening an untrusted repo or letting a beginner experiment without risk of sandbox escape.
✗ Not quite. Not quite: --restricted goes further than a simple network cutoff or a plain manual mode: it also removes the command-execution tools and WebFetch, confines files to the working directory, and forbids any return to bypass mode during the session.
Quick quiz · memoire

How do you prevent an @path/to/file.md path from being automatically imported into CLAUDE.md?

✓ Correct. Correct. Wrapping a path in backticks (@README) prevents it from being automatically imported; without backticks, an @path/to/file.md path is indeed imported, with a maximum depth of 4 hops.
✗ Not quite. Not quite. It's the use of backticks around the path (@README) that blocks the import : HTML comments and import depth don't play that role.
Quick quiz · skills

What does the disallowed-tools field do in a SKILL.md's frontmatter?

✓ Correct. Correct. disallowed-tools shrinks the pool of available tools while the skill runs. This is useful, for example, to prevent AskUserQuestion inside an autonomous loop where no one can answer a question.
✗ Not quite. It's disallowed-tools that removes certain tools from the available pool for the duration of the skill, typically to prevent AskUserQuestion inside an autonomous loop.
Quick quiz · plan

In Claude Code's settings.json, which setting determines where plan mode writes its plan files?

✓ Correct. Correct. The plansDirectory setting chooses where plan mode writes its plan files, and it's resolved relative to the project root, which is useful, for example, for versioning these plans in the repo and reviewing them in a PR.
✗ Not quite. Not quite. It's plansDirectory, resolved relative to the project root, handy for versioning generated plans and reviewing them.
Quick quiz · agents

By default, how many subagents can Claude Code run in parallel within a session?

✓ Correct. Correct. The default cap is 20 concurrent subagents, adjustable via the CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS environment variable; the total per-session cap, for its part, was removed in v2.1.224.
✗ Not quite. Not quite. The default cap is actually 20 concurrent subagents, adjustable via CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS.
Quick quiz · hooks

According to the hooks documentation, which event fires right before a context compaction and can block it with exit code 2?

✓ Correct. PreCompact fires right before a compaction and can block it (exit code 2). PostCompact, on the other hand, fires only right after, which is useful for example for archiving important information before it gets compacted.
✗ Not quite. It's PreCompact: it steps in before the compaction and can block it with exit code 2. PostCompact fires after the fact, once the compaction has already happened, so too late to prevent it.
Quick quiz · mcp

According to the documentation, which MCP transport type is now recommended for a new server?

✓ Correct. Correct. The HTTP streamable transport is recommended wherever possible; SSE remains supported but is explicitly marked deprecated in the documentation.
✗ Not quite. Not quite. HTTP streamable is the recommended one: SSE remains supported, but it's marked deprecated.
Quick quiz · rewind

What exactly does the "Summarize up to here" option in the /rewind menu do?

✓ Correct. Correct. "Summarize up to here" acts only on the conversation history: it compresses it before the chosen point, without modifying the files on disk. That's useful for freeing up context without losing the code work already done.
✗ Not quite. Not quite. This option doesn't touch any files and doesn't create any commit: it only compresses the conversation before the chosen point, leaving the code untouched.
Quick quiz · git

With no special configuration, which reference does a new Claude Code worktree start from by default?

✓ Correct. Correct. worktree.baseRef defaults to "fresh" as of v2.1.133: every new worktree starts from origin/<default branch>. The "head" setting (which must be explicitly enabled) starts from your local HEAD, including unpushed commits.
✗ Not quite. Not quite. The default is "fresh": it starts from origin/<default branch>. "head" also exists, but it's an option you have to enable yourself in order to start from your local HEAD with unpushed commits.
Quick quiz · echelle

What is the cap on recurring tasks that the CronCreate/CronList/CronDelete tools can schedule per session?

✓ Correct. Correct. The cap is 50 recurring tasks per session for the CronCreate/CronList/CronDelete tools; /loop, on the other hand, runs a prompt or a skill at a regular interval directly in the current conversation, without that cap.
✗ Not quite. Not quite. It's 50: the Cron tools (CronCreate/CronList/CronDelete) cap recurring tasks scheduled per session at this number, as distinct from /loop, which runs in the current conversation.
Quick quiz · plugins

For a github/url/git-subdir plugin source, which marketplace.json field pins an exact version of the plugin, independent of future commits on the branch?

✓ Correct. Correct. The sha field (a full git commit) pins a precise version of the plugin, unaffected by later commits pushed to the referenced branch.
✗ Not quite. Not quite. It's the sha field (a full git commit) that pins an exact version, independent of future commits on the branch. There is no version field or tag field for this purpose.
Quick quiz · infra

In which case does the SDK's fallbackModel mechanism never switch to a backup model?

✓ Correct. Correct. fallbackModel accepts up to three models tried in order, but only in case of overload or a server error, never for an authentication, billing, or rate-limit error.
✗ Not quite. Not quite. Overload and server errors do trigger a switch; it's precisely an authentication, billing, or rate-limit error that never activates fallbackModel.
