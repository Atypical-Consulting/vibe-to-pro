Checkpoints & Rewind: The Safety Net

Explore without fear

Vibe-coding chains prompts blindly with no safety net if Claude heads in the wrong direction. Checkpoints turn that improvisation into professional practice: every prompt becomes a restorable point, code and/or conversation, even before a Git commit.

What if a bad prompt only cost you a round trip?

You've probably felt this before in vibe-coding: you chain prompts one after another, Claude touches two or three files each time, and at some point a request heads in the wrong direction. The natural instinct is to fix it by hand, prompt after prompt, hoping to land somewhere close to the previous state. That's exactly the problem checkpoints (restore points, one per step) solve: every prompt you send automatically becomes a point you can return to, with no need to have made a Git commit beforehand to protect yourself.

So how does it actually work? You press Escape twice, or type /rewind, and a menu opens listing these points, one per prompt sent, in order. You can also jump straight to the point by passing an argument directly (a turn number as in /rewind 5, a checkpoint name, or a description) instead of browsing the list. The idea behind splitting by prompt, rather than by a simple file save, is that the unit of work in vibe-coding is the exchange: a request, Claude's response, and the files changed as a result. Going back to "right before this prompt" matches exactly how you think about your mistake.

But what exactly gets restored when you pick a point? Here again the mechanism is designed to match your real need: you can restore code and conversation together, wiping out both the modified files and the trace of the bad request, or restore code only, letting the conversation keep the memory of what happened. That's useful if you want to understand afterward why Claude went in that direction. A third option, "Summarize up to here," answers a different need: it compresses the conversation history before the chosen point, without touching the files on disk. So it's not a tool for undoing a mistake, but for freeing up space in a conversation that's grown too long, without losing the code work already done.

One thing to watch out for, though: this code restoration isn't entirely blind. Symbolic links and hard links (files that point to another file rather than containing their own data) are deliberately skipped during a restore: they keep their current content, and Claude Code explicitly warns you with a message rather than silently changing them. And the safety net isn't limited to the code of a running session either: there's also a complementary reflex for continuity between sessions. --continue picks up directly the most recent conversation in the current directory, while --resume opens a selector or targets a specific session by its ID. Here's what that changes in practice, in detail.

Quick quiz

What exactly does the "Summarize up to here" option in the /rewind menu do?

✓ Correct. Correct. "Summarize up to here" acts only on the conversation history: it compresses it before the chosen point, without modifying the files on disk. That's useful for freeing up context without losing the code work already done.
✗ Not quite. Not quite. This option doesn't touch any files and doesn't create any commit: it only compresses the conversation before the chosen point, leaving the code untouched.
Quick quiz

What's the difference between --continue (-c) and --resume (-r)?

✓ Correct. Correct. --continue (-c) resumes the most recent conversation in the current directory directly, with nothing to choose, while --resume (-r) opens a session selector or resumes a specific session ID you give it.
✗ Not quite. Not quite. The two options aren't interchangeable: --continue automatically resumes the last conversation in the current directory, --resume opens a selector or targets a session by its ID.
Hands-on exercise

Have Claude implement a simple feature, let it modify 2-3 files, then deliberately ask for a change you consider bad. Press Escape twice (or /rewind), pick the point right before it, test "Restore code and conversation," then, on another try, "Restore code" alone.

Solution & verification

Pressing Escape twice (or typing /rewind) opens the checkpoint menu, which lists one restorable point per prompt sent, as described in the fact about /rewind (v2.0.0). This lets you pinpoint unambiguously the turn right before the change you considered bad, rather than counting Git commits. Choosing "Restore code and conversation" on that point brings both the code of the 2-3 modified files and the conversation history back to that state; redoing the attempt with "Restore code" alone restores only the files on disk, while the conversation keeps the trace of the request you considered bad. The expected manipulation therefore comes down to /rewind (or Esc x2), then selecting the checkpoint immediately before the bad request, tested once with each restore option.

  • With "Restore code and conversation": the prompt judged bad and Claude's response that followed visibly disappear from the displayed conversation thread, and the content of the 2-3 modified files matches their state before that prompt (verifiable by reopening them or via a diff).
  • With "Restore code" alone: the file content goes back to the same pre-prompt state, but the conversation thread still fully displays the prompt judged bad and Claude's response. This contrast is what proves only the code restore took place.
  • No message like "Restored the code, but skipped N files" appears for these ordinary files; such a message should only show up if one of the 2-3 files involved is a symbolic or hard link.
