Control & Security: Permissions, Sandbox, Auto Mode

The foundation before everything else

Vibe-coding means letting an agent run commands on the fly without ever stopping to ask what it might break or exfiltrate. Mastering permissions and the sandbox means precisely defining the perimeter: which files Claude can read, which network domains it can reach, which destructive commands stay blocked by default. This forms a reproducible, team-auditable foundation via .claude/settings.json.

Level check

In auto mode, which of these commands is blocked by default?

✓ Correct. A list of destructive commands (git reset --hard, git clean -fd, terraform destroy...) is blocked by default in auto mode; they get lifted case by case when you state the intent explicitly.
→ You already know this lever, skip to the next module

Who really decides what Claude Code is allowed to do?

When you 'vibe-code', you've probably already felt that little vertigo: the agent proposes a command, you approve it without thinking too hard, and at some point you wonder what would happen if it typed git push --force or poked through a folder you didn't want it to see. That's exactly the problem auto mode tries to solve. For a while now, it has even become the default startup mode on the Pro, Max, and Team plans: you just launch claude, with no special flag, and the session already starts in this mode. Shift+Tab lets you switch to another mode at any time. The old 'default' mode, meanwhile, has actually been renamed: it's now called 'Manual' everywhere in the interface, precisely to remind you that it makes you approve each action one by one.

But what does auto mode actually block, to earn your trust? It doesn't ask you to confirm every command, since that would be tedious and you'd end up clicking 'yes' without reading. Instead, it maintains a list of commands recognized as destructive (git reset --hard, git clean -fd, git stash drop, terraform destroy, among others) and blocks them by default, with nothing to configure on your part. The logic is clever: this block isn't final, it lifts case by case when you state the intent explicitly ('force-push this branch'), which keeps you in control without forcing you to watch everything constantly. At the other end of the spectrum, bypass mode (--dangerously-skip-permissions) removes most guardrails, including on normally protected paths like .claude/ or .git/, but a safety net on truly catastrophic deletions (rm -rf / or ~) stays active no matter what; this mode should be reserved for isolated containers or VMs, never your everyday machine. And if you want the opposite (a deliberately narrowed perimeter to open an unfamiliar repo or introduce the tool to a beginner), the --restricted flag goes even further: it removes the command-execution tools and web access, confines file tools to the working directory, and refuses any return to bypass mode, with no way to change your mind mid-session.

There's then a second line of defense, lower in the stack: the sandbox, literally a 'sandbox'. The general idea of a sandbox is simple. Instead of trusting a program at its word, you confine it to a walled-off environment where it technically cannot step outside a given perimeter, even if it tries. Claude Code ships a native sandbox for its Bash tool, built on Seatbelt (macOS's built-in confinement mechanism) and on bubblewrap (its Linux counterpart) under Linux or WSL2. Native Windows, however, isn't supported: you need to go through WSL2 to use it. You turn it on simply with /sandbox in a session, with no extra install on macOS. This sandbox confines file and network access, but it doesn't block any sensitive credential by default: it's up to you to declare sandbox.credentials.files or envVars rules to deny (deny) or mask (mode: "mask") a specific secret, and these settings must live in ~/.claude/settings.json, your personal settings, since they're simply ignored if placed in project settings.

That leaves the question of the team: how do you share these rules without everyone starting from scratch? Claude Code splits this across two files: .claude/settings.json, versioned and shared, for common rules, and .claude/settings.local.json, personal and gitignored, for your own preferences. These rules can even use wildcards in allowed Bash commands, like Bash(npm *) or Bash(git * main). A classic trap: a pattern as broad as that last one also allows git -c ..., which can run an arbitrary program. Hence the value of always checking your rules with --verbose before deploying them. And even in auto mode, the first read of a file located outside the working directory triggers a one-time prompt, letting you choose to allow permanently, block, or ask again next time. Here, in detail, is what that actually changes.

Hands-on exercise

Create (or reuse) a training repo: a disposable repo, never your main one, that you'll return to across the following modules to build up a real .claude/ configuration. In this repo: turn on the sandbox with /sandbox, pick auto mode, then ask Claude to list ~/.ssh and run a git push --force. Watch the network/read block happen, then add a sandbox.credentials.files block in ~/.claude/settings.json with mode: "deny" on a sensitive file, and check the result via the /sandbox → Config tab.

Solution & verification

Claude Code's native sandbox relies on Seatbelt (macOS) or bubblewrap (Linux/WSL2) to genuinely confine the Bash tool's file and network access: once turned on via /sandbox, it therefore blocks reading ~/.ssh and the network connection for git push --force on its own, with no extra configuration. This mechanism, however, doesn't block any particular credential by default: you need to explicitly add a sandbox.credentials.files entry with mode: "deny" to deny access to a specific sensitive file, and this setting must be written in ~/.claude/settings.json (user settings), since these keys are ignored if placed in project settings.

  • The command listing ~/.ssh fails with a denial message issued by the sandbox (file access outside the allowed perimeter) rather than a plain, ordinary Claude Code permission refusal.
  • The git push --force fails on the network side (connection refused or host unreachable) instead of succeeding or simply asking for confirmation.
  • In the /sandbox → Config tab, the targeted file shows the deny rule applied only if it was declared in ~/.claude/settings.json; the same entry placed in project settings doesn't show as active.
