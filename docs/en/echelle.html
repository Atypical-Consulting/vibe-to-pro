Background & Multi-Agent Workflows

Scaling Without Losing Control

In vibe-coding, you fire off a prompt without knowing how many agents are running or how to stop them. Mastering background tasks and workflows means knowing exactly who's doing what, with size and cross-session permission guardrails.

Level check

At most, how many agents can a Workflow run concurrently by default?

✓ Correct. 16 concurrent agents at most, with a total cap of 1000 agents across a workflow's entire run.
→ You already know this lever, skip to the next module
✗ Not quite. It's 16: beyond that, additional calls wait in a queue until a slot frees up.

What if Claude kept working while you closed your laptop?

In vibe-coding, you've probably picked up this habit: one prompt, you wait for the response, you fire another. The whole session runs in a single thread, right in front of you, and stops the moment you close the terminal. But what if you want Claude to explore three approaches in parallel, or keep running an audit while you're at lunch? That's where background sessions come in: a task launched this way keeps running without blocking your screen, and a dedicated view (claude agents) groups all these sessions by state (waiting for input, working, completed), so you always know who's doing what without having to keep every window open.

Once you've had a taste of that, the temptation to scale up is strong: why not have dozens of agents working at once on the same project? That's exactly what the Workflow tool is for: it orchestrates potentially hundreds of background agents, organized with simple primitives: launch a single agent, launch several in parallel, or chain them into a pipeline. But a system that can mobilize that much resource without direct supervision needs guardrails: without a cap, nothing stops a poorly scoped workflow from saturating your machine or your API budget within minutes. That's why, for the Workflow tool specifically (a limit distinct from the one mentioned for simple sub-agent delegation), a default maximum of 16 active agents at once exists (beyond that, new calls wait in a queue), with a total cap of 1000 agents per run. A size guideline even tightens things further, targeting a workflow of fewer than 15 agents by default rather than leaving the scale wide open as it used to be.

Scaling without losing control isn't just about limiting the number of agents: it's also about being able to act on each one individually, the way you would with a regular process. A background session can be resumed, inspected via its logs, cleanly stopped, restarted, or removed: a full lifecycle, so you never have a ghost task running without your knowledge. And when several sessions are working on related parts of the same project, they can even flag things to each other, including simply by mentioning one of them in your prompt: you don't need to orchestrate the communication yourself, Claude handles it. A monitoring tool rounds things out by streaming what's happening in a script launched in the background, without ever pausing your conversation.

One question remains: how do you know when a background agent should stop, if no one's there to tell it? That's the role of a task completion condition you state in natural language: Claude then continues across multiple turns, and a small model evaluates at each step whether the condition is met, until it stops automatically. This same principle of bounded autonomy shows up in recurring tasks: scheduling a prompt to repeat at a regular interval, again with a per-session cap to avoid a silent buildup of forgotten tasks. Here's what that changes in practice.

Hands-on exercise

Run the following command to start a background audit:

claude --bg "audit the repo's TODOs"

Open claude agents, pin the session (Ctrl+T), then check its logs with claude logs <id>. Then, on a small task, try the following command to watch Claude loop on its own until the condition is met:

/goal all tests pass and lint is clean
Solution & verification

Running the following command creates a background session:

claude --bg "audit the repo's TODOs"

The full-screen claude agents view groups sessions by state (Needs input / Working / Completed), which makes it easy to spot and pin the right session. The claude logs <id> command is part of the same set of subcommands as attach, stop, respawn, and rm, which together cover a background session's full lifecycle: it lets you check the logs without interrupting the session. The following test works because this directive sets a task completion condition that Claude re-evaluates turn after turn via a small model, until the condition is judged met:

/goal all tests pass and lint is clean
  • In claude agents, the session moves from "Working" to "Completed" once the TODO audit is done, and a pin icon stays visible after Ctrl+T.
  • claude logs <id> returns the session's output stream (the list of TODOs found in the repo) with no "session not found"-style error.
  • After /goal all tests pass and lint is clean, the conversation runs through several turns with no new input from you, ending in a final message confirming the condition is met; you can also interrupt the loop beforehand with /goal clear.
