SDK, Headless Mode, CI/CD & IDE

Turning Claude Code into an infrastructure building block

Vibe-coding validates every action by gut feel in interactive mode: that doesn't scale. Headless mode and the SDK turn Claude Code into a reproducible building block: deterministic scripts, explicit guardrails, structured output you can act on in CI.

Level check

Which flag skips the automatic discovery of hooks, skills, subagents, plugins, MCP, and CLAUDE.md?

✓ Correct. This is the recommended mode for any scripted or SDK call: predictable behavior, with no implicit local configuration.
→ You already know this lever, skip to the next module
✗ Not quite. It's --bare: it eliminates all automatic discovery of local configuration for predictable, scripted behavior.

What if no one was there to click "Yes"?

In interactive mode, everything is simple: you see what Claude Code is about to do, and you approve or correct it as you go. But what happens when you want to hook Claude Code into a CI/CD pipeline (the system that builds and tests your code automatically on every push) running at 3am with no one watching the screen? Or when you want to call it from your own program, like a plain function? Interactive mode, with its confirmation prompts and implicit local configuration, no longer makes sense then: you need behavior that stays identical on every run, with no surprises and no dependency on whatever happens to be lying around on your machine.

That's exactly the role of headless mode (no interface, driven purely by the command line) and the --bare flag. --bare wipes the slate clean: it skips all automatic discovery of hooks, skills, subagents, plugins, MCP servers, memory, and the CLAUDE.md file. The result: only what you pass explicitly on the command line determines the session's behavior, which makes it reproducible from one machine to another. Combined with --permission-prompts none, which automatically turns into a refusal any action that would normally have triggered a confirmation prompt, you get a script that never sits stuck waiting for a human response that will never come. The SDK, now renamed Claude Agent SDK, formalizes the same logic in code: instead of typing a command, your program drives a Claude Code session directly.

But a script running unsupervised also has to know how to protect itself, on its own turf. The SDK's canUseTool callback is a good illustration of this layered caution: it only gets called if nothing upstream of it (a PreToolUse hook, an allow/deny/ask rule, the permission mode) has already decided, which lets you add custom business validation without duplicating what already exists. The same cautious logic applies to resilience: the fallbackModel mechanism automatically switches to a backup model in case of overload or a server error, but never for an authentication, billing, or rate-limit error. Switching models wouldn't fix those problems anyway: better for the job to fail clearly than to mask a real incident. As for maxBudgetUsd, it caps the spend of an automated run: nobody is watching the meter live, so the setting itself has to cut things off before the bill gets out of hand.

One last problem remains: how does a pipeline know, with no human to read the screen, that everything went well? By producing structured output rather than text that has to be interpreted by eye. In --output-format stream-json, the system/init message exposes, for example, a plugin_errors field that lists plugin-loading errors (absent if there are none), which gives you a simple validation gate to write into a CI script. On the keyboard-work side rather than the pipeline side, the same CLI shows up embedded in the VS Code extension (side panel, inline diffs, @ mentions tied to the current selection), and /statusline keeps you informed live about the model, cost, and context in use. Here, in detail, is what that changes in practice.

Hands-on exercise

Write the following command:

claude --bare -p "Summarize the last 3 commits" --allowedTools "Bash(git log *)" --permission-mode auto --permission-prompts none --output-format json

Inspect the output with jq to extract .result and .total_cost_usd.

Solution & verification

The command works because --bare eliminates all automatic discovery of hooks, skills, subagents, plugins, MCP, memory, and CLAUDE.md: only what's passed explicitly on the command line (here --allowedTools "Bash(git log *)") determines the behavior, which makes the call reproducible for a script. Combined with --permission-prompts none, which automatically turns into a refusal any action that would normally have triggered a confirmation prompt, the job stays non-interactive from start to finish: any command outside the git log scope gets rejected without waiting for a human response. --output-format json then produces a single JSON object from which jq extracts .result (the summary) and .total_cost_usd (the cost of the call).

  • The command exits with status code 0 and prints a single JSON object to stdout (not multiple lines, since the format isn't stream-json).
  • jq -r '.result' returns non-empty text that properly summarizes the last 3 commits, and jq '.total_cost_usd' returns a positive decimal number (never null).
  • No confirmation prompt appears during execution; had a command outside the Bash(git log *) scope been attempted, it would have been automatically refused instead of blocking the terminal while waiting for approval.
