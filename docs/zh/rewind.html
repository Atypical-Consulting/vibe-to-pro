检查点 & Rewind：安全网

无所畏惧地探索

Vibe Coding 只是盲目地一个接一个发 prompt，一旦 Claude 走偏就没有任何退路。检查点把这种即兴操作变成专业做法：每一个 prompt 都成为一个可恢复的还原点，涵盖代码和／或对话，甚至不需要先做一次 Git commit。

水平测试

自 v2.1.216 起，/rewind 在恢复代码时会跳过哪些文件？

✓ 正确。这些文件会保留当前内容，并给出一条「Restored the code, but skipped N files」提示。对于用符号链接管理的 dotfiles，这一点值得知道。
→ 你已经掌握这一手段，直接进入下一模块
✗ 不完全正确。被跳过的是符号链接和硬链接（hard links），而不是 .env 或二进制文件。

如果一个失败的 prompt 只需一次往返就能挽回呢？

你多半已经熟悉 Vibe Coding 中的这种感觉：你一个接一个地发 prompt，Claude 每次改动两三个文件，然后某一次请求突然走偏了。本能的反应是手工补救，一个 prompt 接一个 prompt 地改，指望大致回到之前的状态。检查点（还原点，每一步一个）要解决的正是这个问题：你发出的每一个 prompt 都会自动成为一个可以回退到的点，而不需要事先做一次 Git commit 来保护自己。

具体怎么用？连按两次 Esc，或者输入 /rewind，就会打开一个菜单，按顺序列出这些还原点：每发出一个 prompt 就有一个。你也可以直接传入参数一步到位（轮次编号，例如 /rewind 5、检查点名称或一段描述），而不必翻看整个列表。之所以按 prompt 而不是按单纯的文件保存来划分，是因为 Vibe Coding 的工作单元就是一次交流：一个请求、Claude 的一次回应、以及随之改动的文件。回到「就在这个 prompt 之前」，正好对应你思考自己错误的方式。

那么选中一个还原点时，究竟恢复了什么？这里的机制同样贴合真实需求：你可以同时恢复代码和对话，一并抹掉改动过的文件和那次错误请求的痕迹；也可以只恢复代码，让对话保留发生过什么的记录。如果你想事后弄清 Claude 为什么会走上那个方向，这很有用。第三个选项「Summarize up to here」满足的是另一种需求：它压缩所选点之前的对话历史，完全不动磁盘上的文件。所以它不是用来挽回错误的工具，而是在对话拉得太长时腾出空间，同时不丢失已经完成的代码工作。

不过仍有一点需要留意：代码恢复并非完全不加区分。符号链接和硬链接（这类文件指向另一个文件，本身并不存放数据）在恢复时会被有意跳过：它们保留当前内容，Claude Code 会用一条提示明确告知你，而不是悄悄修改它们。安全网也不止于当前会话内的代码，跨会话的连续性还有一个互补的习惯：--continue 会直接恢复当前目录中最近的一次会话，而 --resume 会打开一个选择器，或通过标识符定位到指定会话。下面详细说明这在实践中带来什么改变。

✓ 正确。正确。「Summarize up to here」只作用于对话历史：它压缩所选点之前的内容，不修改磁盘上的文件。这适合在不丢失已完成代码工作的前提下腾出上下文空间。
✗ 不完全正确。不完全正确。这个选项不碰任何文件，也不创建任何 commit：它只压缩所选点之前的对话，代码保持不变。
快速测验

--continue (-c) 和 --resume (-r) 有什么区别？

✓ 正确。正确。--continue (-c) 直接恢复当前目录中最近的一次会话，无需做任何选择；而 --resume (-r) 会打开会话选择器，或恢复你指定的某个会话 ID。
✗ 不完全正确。不完全正确。这两个选项并不可以互换：--continue 自动恢复当前目录中最近的一次对话，--resume 打开一个选择器或按 ID 定位某个会话。
实践练习

让 Claude 实现一个简单功能，让它改动 2 到 3 个文件，然后故意提出一个你认为糟糕的修改要求。连按两次 Esc（或 /rewind），选择就在那之前的还原点，先试「Restore code and conversation」，再在另一次尝试中只用「Restore code」。

解答 & 验证

连按两次 Esc（或输入 /rewind）会打开检查点菜单，其中每发出一个 prompt 就列出一个可恢复的还原点，正如关于 /rewind 的事实（v2.0.0）所描述。这样就能毫不含糊地找到那次糟糕修改之前的轮次，而不用去数 Git commit。在这个还原点上选择「Restore code and conversation」，被改动的 2 到 3 个文件的代码和对话历史都会回到那个状态；再用「Restore code」重做一次，则只恢复磁盘上的文件，对话仍保留那次糟糕请求的痕迹。因此预期操作就是：/rewind（或连按两次 Esc），选中紧邻糟糕请求之前的检查点，两种恢复选项各测试一次。

  • 使用「Restore code and conversation」时：那个糟糕的 prompt 以及 Claude 随后的回应会明显从显示的对话流中消失，被改动的 2 到 3 个文件的内容回到该 prompt 之前的状态（重新打开文件或用 diff 即可验证）。
  • 只用「Restore code」时：文件内容同样回到该 prompt 之前的状态，但对话流依然完整显示那个糟糕的 prompt 和 Claude 的回应。正是这一对比证明只发生了代码恢复。
  • 对这些普通文件不会出现「Restored the code, but skipped N files」之类的提示；只有当这 2 到 3 个文件之一是符号链接或硬链接时，才应该出现这种提示。
