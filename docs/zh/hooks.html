Hooks：不依赖模型的自动化

确定性的规则，而不是一厢情愿

在 Vibe Coding 中，我们让模型自己决定何时格式化、何时跑测试、何时请求确认，而它有时会忘记。Hooks 把这些习惯变成规则，让它们 始终 在正确的时刻执行，可脚本化，也可在团队中共享。

如果最佳实践能自己执行，不用你反复提醒，会怎么样？

在 Vibe Coding 中，我们都遇到过这种情况：你让 Claude 在提交前跑测试，或者把代码格式化干净。十次里有九次它会照做。可某一天它就忘了，因为它急着去回应别的事。这并不反常：在每一步，模型都自己决定要做什么，而一个决定，哪怕在绝大多数情况下都是对的，终归只是决定，不是保证。hook 彻底改变了这一点：它是一条你只写一次的规则，只要会话中发生某个特定事件，它就会自动执行，无论模型是否想得起来。

具体是怎么运作的？hook 挂接到 Claude Code 生命周期中的某个事件（工具执行之前、工具执行之后、上下文压缩之前，压缩会把对话总结掉以腾出空间，还有很多其他事件），并在那一刻触发你定义的动作：运行本地脚本 (type: "command")，直接调用已安装的 MCP 工具并对事件字段做插值 (type: "mcp_tool")，或者把事件的 JSON 以 POST 发送到外部服务并等待它的响应 (type: "http")。你甚至可以非常精确地控制 hook 何时触发，靠的是一个 if 字段，它沿用权限规则的语法，比如只对 git 命令做出反应，写成 Bash(git *)。hook 不会向模型征询任何意见：它就是执行，仅此而已，这让它成为确定性的安全网，而不是一种期望。

但 hook 未必是一道把一切拦停的屏障。有意思的地方正在这里：在 hook PostToolUse 上（它在工具被使用之后立即触发），选项 continueOnBlock: true 可以把阻断原因作为一个普通的工具结果返回给 Claude，而不是粗暴地终止这一轮。比如一次失败的类型检查，就可以顺势由 Claude 自动修好，你自己不用重新跑任何东西。在会话的另一端，一个 PreCompact hook 甚至可以直接阻止压缩发生（返回退出码 2），好让你在历史被总结之前先归档重要内容。

而且因为这些规则可以写在整个团队共享的配置文件里，甚至可以通过某个 skill 或 agent 的 frontmatter把它们限制在该 skill 或 agent 的生命周期之内，所有人就都在同一套护栏下工作，不必每次会话都重复同样的叮嘱。下面详细看看这到底改变了什么。

快速测验

根据 hooks 文档，哪个事件会在上下文压缩之前触发，并且可以用退出码 2 阻止压缩？

✓ 正确。PreCompact 在压缩之前触发，并且可以阻止压缩（退出码 2）。PostCompact 则只在压缩之后触发，这在压缩前归档重要信息之类的场景里很有用。
✗ 不完全正确。答案是 PreCompact：它在压缩之前介入，可以用退出码 2 阻止压缩。PostCompact 在事后触发，此时压缩已经完成，想阻止已经太晚。
快速测验

哪种 hook 类型可以直接调用已安装的 MCP 工具，并对 hook 输入 JSON 中的字段做插值？

✓ 正确。mcp_tool 类型直接调用已安装的 MCP 工具，并对 hook 输入 JSON 中的字段做插值。比如可以把一项安全检查交给现成的 MCP 工具，不必再写 shell 脚本。
✗ 不完全正确。答案是 mcp_tool 类型：它可以直接调用已安装的 MCP 工具，并对 hook 输入 JSON 中的字段做插值，而不是执行脚本 (command) 或发送网络请求 (http)。
实践练习

创建一个 PreToolUse hook，作用于 Bash，并设置 if: "Bash(rm *)" 从而用退出码 2 阻断所有 rm 命令。再添加一个 PostToolUse hook，作用于 Edit|Write 并设置 continueOnBlock: true 让它运行一个 linter，把错误返回给 Claude，而不是终止这一轮。查看 /hooks 可以看清每个生效 hook 的来源。

解答 & 验证

第一个 hook 依靠 if 字段，它接受权限规则的语法（例如 Bash(git *)），可以精确定位到某个子命令。写成 if: "Bash(rm *)" 时，PreToolUse hook 只在 rm 命令上触发，而以退出码 2 结束的脚本会阻断这次工具调用。第二个 hook 用到 PostToolUse 上的 continueOnBlock: true 选项，它把阻断原因作为工具结果返回给 Claude，而不是终止这一轮。这样一来，报错的 linter 可以由 Claude 自动修复，而不是中断会话。因此最终期望的配置是 hooks 配置里的两条条目：一条在 PreToolUse 上（matcher 为 Bash，if: "Bash(rm *)"，命令以退出码 2 结束），一条在 PostToolUse 上（matcher 为 Edit|Write，continueOnBlock: true，命令运行 linter）。

  • Claude 尝试执行的 rm 命令会被立即拒绝：Bash 工具不会运行，hook 返回的错误信息（退出码 2）会作为工具结果出现在对话中。
  • 在通过 Edit 或 Write 做出修改并让 linter 报错之后，这一轮不会停下：linter 的错误会作为工具结果出现，Claude 会在下一条消息里给出修正，而不是让会话中断。
  • /hooks 命令确实会把两个 hook 都列为生效状态，并显示它们的来源（声明它们的 settings 文件）以及各自的 matcher：PreToolUse hook 是 Bash，PostToolUse hook 是 Edit|Write。
