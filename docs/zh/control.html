控制 & 安全：权限、沙箱与自动模式

一切的地基

Vibe Coding 就是让代理随手执行命令，却从不追问它可能破坏什么、又可能把什么带出去。掌握权限与沙箱，就是把范围划清楚：Claude 能读哪些文件、能访问哪些网络域名、哪些破坏性命令默认保持拦截。这会形成一份可复现、可在团队中审计的基础配置，靠的是 .claude/settings.json。

水平测试

在自动模式下，以下哪条命令默认会被拦截？

✓ 正确。一批破坏性命令（git reset --hard, git clean -fd, terraform destroy…）在自动模式下默认被拦截；只要你明确表达意图，就会逐条放行。
→ 你已经掌握这一环，直接进入下一模块
✗ 不完全正确。在自动模式下默认被拦截的是 git reset --hard 以及其他破坏性命令，而不是只读命令，例如 git status 或 git commit。

到底是谁在决定 Claude Code 有权做什么？

当你在做 Vibe Coding 时，多半已经体会过那种轻微的眩晕：代理提议一条命令，你没怎么细想就点了同意，然后某一刻突然想到，要是它敲的是 git push --force，或者去翻一个你并不想让它看到的目录，会发生什么。这正是自动模式想要解决的问题。一段时间以来，它已经成为 Pro、Max 和 Team 套餐的默认启动模式：你只需运行 claude，不带任何额外标志，会话就已经处于该模式。Shift+Tab 可以随时切换到其他模式。至于原来的「默认」模式，它也改了名字：现在整个界面里都叫「Manual」，正是为了提醒你，它要求你逐个确认每一次操作。

但自动模式究竟拦截了什么，才配得上你的信任？它不会要求你确认每一条命令，因为那样太繁琐，你最后只会不看内容就点「是」。取而代之的是，它维护一份公认具有破坏性的命令清单（git reset --hard, git clean -fd, git stash drop, terraform destroy等），并默认拦截它们，你什么都不用配置。这个设计很巧妙：拦截并非不可撤销，只要你明确表达意图（「强推这个分支」），就会逐条放行，既把主动权留给你，又不必时刻盯着。在标尺的另一端，bypass 模式（--dangerously-skip-permissions）移除了大部分护栏，包括那些通常受保护的路径，例如 .claude/ 或 .git/，但针对真正灾难性删除的安全网（rm -rf / 或 ~）无论如何都保持生效；这个模式只应留给隔离的容器或虚拟机，绝不要用在你的日常机器上。如果你想要的恰恰相反（为打开一个陌生仓库、或让新手上手而主动收窄范围），--restricted 标志走得更远：它移除命令执行工具和网页访问，把文件工具限制在工作目录内，并拒绝切回 bypass 模式，会话中途无法反悔。

接下来还有第二道防线，位于更底层：沙箱，字面意思就是「装沙子的盒子」。沙箱的总体思路很简单。与其听信一个程序的口头承诺，不如把它关进一个隔离环境，让它在技术上根本走不出既定范围，哪怕它想。Claude Code 为它的 Bash 工具内置了原生沙箱，依托 Seatbelt（macOS 自带的隔离机制），在 Linux 或 WSL2 上则依托 bubblewrap（Linux 侧的对应实现）。原生 Windows 则不受支持：要用上它必须走 WSL2。你只需在会话中运行 /sandbox 即可启用，在 macOS 上无需额外安装。这个沙箱会限制文件和网络访问，但默认不会拦截任何敏感凭据：需要你自己声明 sandbox.credentials.files 或 envVars 规则，用来拒绝（deny）或掩码（mode: "mask"）某个具体的密钥，而这些设置必须写在 ~/.claude/settings.json，也就是你的个人设置里，因为一旦放进项目设置，它们会被直接忽略。

还剩团队协作的问题：怎样共享这些规则，才不用每个人从零开始？Claude Code 把它拆成两个文件：.claude/settings.json，纳入版本控制并共享，存放公共规则；以及 .claude/settings.local.json，属于个人、被 gitignore 忽略，存放你自己的偏好。这些规则甚至可以在允许的 Bash 命令里使用通配符，比如 Bash(npm *) 或 Bash(git * main)。一个经典陷阱：后者这么宽的模式同时也放行了 git -c ...，而它可以执行任意程序。所以务必先用 --verbose 检查规则，再把它们发布出去。而且即便在自动模式下，首次读取工作目录之外的文件也会触发一次性确认提示，让你选择永久允许、拦截，或者下次再问。下面具体看看这带来了什么变化。

实践练习

创建（或复用）一个 练习仓库：一个可以随时丢弃的仓库，绝不要用你的主仓库，后续模块会一直沿用它，逐步积累一份真正的 .claude/ 配置。在这个仓库里：用 /sandbox 启用沙箱，选择自动模式，然后让 Claude 列出 ~/.ssh 并执行一次 git push --force。观察网络与读取被拦截的情况，然后在 ~/.claude/settings.json 中添加一个 sandbox.credentials.files 块，配上 mode: "deny"，作用于某个敏感文件，再通过 /sandbox → Config 标签页确认结果。

解答 & 验证

Claude Code 的原生沙箱依托 Seatbelt（macOS）或 bubblewrap（Linux/WSL2），真正限制 Bash 工具的文件与网络访问：一旦通过 /sandbox 启用，它自身就会拦截对 ~/.ssh 的读取，以及 git push --force 的网络连接，无需额外配置。但这套机制默认不会拦截任何特定凭据：必须显式添加一条 sandbox.credentials.files 条目，并带上 mode: "deny"，才能拒绝访问某个具体的敏感文件；而且这项设置必须写在 ~/.claude/settings.json（用户设置）里，因为这些键放在项目设置中会被忽略。

  • 列出 ~/.ssh 的命令会失败，并返回沙箱发出的拒绝信息（文件访问超出授权范围），而不是 Claude Code 常规的权限拒绝。
  • git push --force 会在网络层失败（连接被拒绝或主机不可达），而不是成功执行或仅仅要求确认。
  • 在 /sandbox → Config 标签页中，只有当目标文件声明在 ~/.claude/settings.json 里时，它才会显示为已应用 deny 规则；同样的条目放在项目设置中不会显示为生效。
