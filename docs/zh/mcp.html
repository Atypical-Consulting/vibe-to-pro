MCP（安全地接入外部工具）

Model Context Protocol

在 Vibe Coding 阶段，我们随手接入 MCP 工具，既不知道是谁批准的，也不知道它们能读到什么。走向专业，就是掌握作用域（纳入版本管理的 .mcp.json 文件）、审批机制以及 allowlist/denylist。

水平测试

未获批准的项目作用域 MCP 服务器会显示什么状态，其声明位于 .mcp.json?

✓ 正确。绝不会有静默的自动批准。运行 claude mcp list 会显示每个已配置服务器的审批状态。
→ 你已经掌握了这个要点，直接进入下一个模块
✗ 不完全正确。答案是「Pending approval」：未获批准的项目作用域 MCP 服务器绝不会静默连接。

接到你项目上的这个 MCP 工具，究竟是谁批准的？

你多半已经从某处复制过一条命令，就这样接上了一个 MCP 服务器，却不太清楚它连上之后能做什么。它跑起来了，工具出现了，于是继续往前走，直到某一天你开始问：这东西到底能访问哪些数据，又是谁确认它可以连进来的？MCP 服务器（即 Model Context Protocol）并不是一个简单的本地脚本：它是通往某个外部工具或服务的网关，拥有自己的凭据和自己的权限。理解 Claude Code 如何管束这道网关，正是「碰巧在你机器上能跑」的配置与可以在团队里共享、审计并信赖的配置之间的区别。

这套机制首先关乎作用域，也就是 scope：MCP 服务器可以声明为 local（只对你、只在这个项目里生效），也可以声明为 user 作用域（在你工作的任何地方都生效），还可以声明为 project。最后这种作用域在团队里最有用，因为它存放在一个与其余代码一起提交的 .mcp.json 文件中：任何克隆该仓库的人都会自动拿到同一份 MCP 服务器清单，无需手工重新配置。但把配置放进 Git 共享，并不等于可以不看一眼就运行它，而 Claude Code 正是在这里设了一道护栏。

那么具体来说，当你第一次打开一个包含他人添加的 .mcp.json 的项目时，会发生什么？Claude Code 绝不会静默连接作用域为 project 的服务器，除非它已获批准：在此之前，它会一直显示为 Pending approval 状态（即等待批准），你也可以随时用 claude mcp list 查看。这条规则（绝不自动批准）防的是一种简单却真实的情形：有人往仓库里塞一个配置文件，第一次启动就悄悄把某个工具接到你的文件或凭据上。

服务器获批之后，你个人仍然可以通过 allowedMcpServers 和 deniedMcpServers 这两份列表继续把关。它们通过名称、URL 或命令来识别服务器（支持通配符），也适用于在企业范围内部署的服务器。协议还规定了数据如何在你与服务器之间流动：目前推荐使用 HTTP streamable 传输，而旧的 SSE 仍然受支持，但文档中已明确标注为弃用。换句话说，保护一个 MCP 工具，不只是决定它有没有权限连接，还包括它以什么方式连接。下面来看这具体带来哪些变化。

实践练习

在项目根目录创建一个 .mcp.json 文件，配置一个公开的 HTTP MCP 服务器，然后运行 claude。观察出现的「Pending approval」提示，接受它，然后用 claude mcp list 验证。随后为你自己屏蔽同一个服务器：把它写进 deniedMcpServers 列表，该列表位于 ~/.claude/settings.json.

解答 & 验证

在根目录创建 .mcp.json 文件，会把服务器放到 project 作用域：正是这个被提交的文件让团队可以通过 Git 共享配置，但任何尚未批准的条目都会显示「Pending approval」，而不会静默连接（绝不自动批准）。团队层面批准之后，个人层面的屏蔽则通过 deniedMcpServers 实现，它位于 ~/.claude/settings.json，按 serverName, serverUrl 或 serverCommand :

{ "deniedMcpServers": [{"serverName": "server-name"}] }
  • 启动 claude 时，在任何连接尝试之前，.mcp.json 中的那个服务器会准确显示「Pending approval」消息。
  • 接受之后，运行 claude mcp list 会显示该服务器的审批状态已变为已批准（而不是 Pending）。
  • 加入 deniedMcpServers 条目并重启 claude 之后，这个服务器对你不再显示为可用/已连接（它的工具不再出现），但对团队其他人仍然有效。
