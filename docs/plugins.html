Plugins & marketplaces

Outiller toute l'équipe, pas juste soi

En vibe‑coding, on installe un plugin trouvé au hasard et on croise les doigts. En pro, les plugins et marketplaces donnent la reproductibilité (version épinglée par SHA), la sécurité (secrets jamais injectés en shell) et la gouvernance (activation explicite, coût en tokens visible).

✗ Pas tout à fait. Il faut lancer claude plugin enable <nom> : l'installation seule ne suffit pas à activer un plugin marqué defaultEnabled: false.

Un plugin trouvé sur GitHub, vous l'installez… et ensuite ?

Un plugin, c'est tentant : quelqu'un l'a codé, vous l'installez, et Claude Code sait soudain faire une chose de plus. En vibe-coding, c'est souvent tout ce qu'on demande. Ça marche, on continue. Mais un plugin n'est pas qu'une commande en plus : il peut apporter des agents, des hooks (des scripts qui se déclenchent automatiquement à certains moments) et même des serveurs MCP ou LSP entiers (LSP, pour Language Server Protocol, le protocole qui donne à un éditeur la compréhension fine d'un langage de programmation), le tout empaqueté et distribué via une marketplace, une sorte de catalogue partagé. Et c'est là que ça devient intéressant pour une équipe : en déclarant cette marketplace une seule fois dans .claude/settings.json via extraKnownMarketplaces, tout le monde y accède sans rien réinstaller de son côté.

Mais installer un plugin ne veut pas dire l'activer, et c'est un choix de conception assumé. Si son auteur a mis defaultEnabled: false dans le plugin.json, le plugin reste inerte tant que vous n'avez pas lancé vous-même claude plugin enable <nom>. Pourquoi cette étape qui semble redondante ? Parce qu'un plugin qui s'activerait tout seul à l'installation agirait sur votre projet avant même que vous ayez décidé de lui faire confiance. Et avant de franchir ce pas, vous pouvez interroger claude plugin details <nom> : la commande liste ce que le plugin embarque et projette le coût en tokens qu'il ajoutera à chaque session. Vous savez ainsi ce que vous activez avant de l'activer, pas après.

Reste un problème classique : un plugin qui pointe vers une branche GitHub peut changer sous vos pieds, un commit poussé la semaine prochaine n'étant pas celui que vous avez testé aujourd'hui. C'est pour ça que marketplace.json peut épingler un sha, un commit git complet, comme une photo figée plutôt qu'un flux qui continue de bouger. Même logique quand le plugin n'est même pas sur git : une source de type archive installe directement un zip via HTTPS, sans git ni npm, avec elle aussi un hachage SHA-256 optionnel pour garantir que le contenu reçu est bien celui attendu. Résultat : ce que vous avez testé est, au commit près, ce qui tournera chez votre collègue ou en CI.

Il reste la question de la confiance côté configuration et sécurité. Un dépôt cloné pourrait-il glisser discrètement ses propres réglages de plugins dans votre session ? Non : pluginConfigs n'est plus lu depuis les settings de projet, seuls vos settings utilisateur, --settings ou les settings managés par votre organisation comptent. C'est la commande /plugin qui les écrit, dans votre ~/.claude/settings.json à vous. Même vigilance du côté des hooks d'un plugin : la substitution ${user_config.*} en forme shell est bloquée, car elle ouvrirait une faille d'injection si une valeur de configuration contenait du code malveillant ; il faut passer par la forme exec ou lire la variable d'environnement $CLAUDE_PLUGIN_OPTION_<CLE>. Voici, en détail, ce que ça change concrètement.

Exercice pratique

Lancez la commande suivante :

claude plugin init mon-plugin --with skills hooks

Ajoutez "defaultEnabled": false dans le plugin.json généré, puis vérifiez qu'il faut lancer la commande suivante pour l'activer :

claude plugin enable mon-plugin

Exécutez enfin cette commande pour voir son coût en tokens projeté par session :

claude plugin details mon-plugin
Solution & vérification

Le plugin.json généré par claude plugin init n'active rien tout seul. Dès que vous y ajoutez "defaultEnabled": false, la référence des plugins exige une activation explicite avant que le plugin ne soit actif, même une fois installé. C'est exactement pourquoi claude plugin enable mon-plugin devient une étape obligatoire et non facultative. Une fois le plugin activé, claude plugin details mon-plugin liste ses composants déclarés (ici les skills et hooks demandés via --with skills hooks) et projette leur coût en tokens par session avant même que vous n'ayez à les utiliser, ce qui permet de juger son empreinte sans le laisser tourner à l'aveugle.

  • Avant claude plugin enable, une commande/skill du plugin invoquée dans la session échoue ou reste invisible, et claude plugin list (ou /plugin dans le REPL) affiche mon-plugin avec un statut désactivé.
  • claude plugin enable mon-plugin se termine avec un code de sortie 0 et fait passer mon-plugin au statut actif dans claude plugin list.
  • claude plugin details mon-plugin affiche une estimation chiffrée du coût en tokens par session (une valeur numérique), en plus de la liste des skills et hooks déclarés, pas seulement les noms des composants.
