Cours de terrain — Claude Code

Du vibe‑coding à une pratique professionnelle

Ce manuel part du CHANGELOG officiel de Claude Code (385 versions, de 0.2.21 à 2.1.260) et vérifie chaque fonctionnalité contre la documentation actuelle sur code.claude.com. L'objectif : transformer des réflexes de « prompt et on espère » en pratiques contrôlées, reproductibles et sûres.

Source primaire : github.com/anthropics/claude-code/CHANGELOG.md Vérifié au : 2 sept. 2026 — Claude Code v2.1.260 Méthode : changelog → recherche documentaire → verdict par fait
00

Le vibe‑coding s'arrête où commence le contrôle

Vibe‑coder, c'est taper un prompt et espérer. Pratiquer Claude Code en pro, c'est savoir précisément ce que l'outil va faire, pouvoir le prouver, le rejouer et le confier à une équipe. Ce cours suit douze leviers de contrôle, dans l'ordre où un développeur devrait se les approprier : d'abord la sécurité, puis la mémoire et les commandes, puis la délégation à des sous‑agents, puis l'échelle en équipe.

  • « Je laisse tourner et je croise les doigts »→Un périmètre de permissions explicite, un sandbox actif, des règles versionnées
  • « Je réexplique le contexte à chaque session »→CLAUDE.md + mémoire automatique, chargés et audités via /context
  • « Je retape le même prompt de mémoire »→Une commande /nom versionnée dans .claude/skills/
  • « Un seul fil, tout se mélange »→Des sous‑agents isolés, un modèle par tâche, une profondeur maîtrisée
  • « J'espère qu'il va formatter et tester »→Des hooks déterministes qui s'exécutent toujours au bon moment
01

Contrôle & sécurité — permissions, sandbox, mode auto

La fondation avant tout le reste

Le vibe‑coding, c'est laisser un agent exécuter des commandes au fil de l'eau sans jamais se demander ce qu'il pourrait casser ou exfiltrer. Maîtriser les permissions et le sandbox, c'est définir précisément le périmètre : quels fichiers Claude peut lire, quels domaines réseau il peut joindre, quelles commandes destructrices restent bloquées par défaut — un socle reproductible et auditable en équipe via .claude/settings.json.

Ce qu'il faut retenir

Exercice pratique

Dans un projet de test (jamais votre dépôt principal) : activez le sandbox avec /sandbox, choisissez le mode auto, puis demandez à Claude de lister ~/.ssh et de faire un git push --force. Observez le blocage réseau/lecture, puis ajoutez dans ~/.claude/settings.json un bloc sandbox.credentials.files avec mode: "deny" sur un fichier sensible, et vérifiez le résultat via l'onglet /sandbox → Config.

Quiz éclair

En mode auto, laquelle de ces commandes est bloquée par défaut ?

✓ Exact. Une liste de commandes destructrices (git reset --hard, git clean -fd, terraform destroy…) est bloquée par défaut en mode auto ; elles se lèvent au cas par cas si vous formulez l'intention explicitement.
✗ Pas tout à fait. C'est git reset --hard qui est bloqué par défaut en mode auto, avec d'autres commandes destructrices — pas les commandes de lecture comme git status ou git commit.
02

Mémoire — CLAUDE.md et mémoire automatique

Arrêter de tout réexpliquer à chaque session

En vibe‑coding, chaque session repart de zéro : on répète les mêmes conventions, les mêmes corrections. Maîtriser CLAUDE.md et la mémoire automatique transforme ce contexte volatil en configuration versionnée, partagée en équipe et auditable via /context.

Ce qu'il faut retenir

Exercice pratique

Lancez /init pour générer un CLAUDE.md de base, ajoutez une règle précise (« utilise pnpm, jamais npm »), puis corrigez volontairement Claude sur une préférence pendant une tâche. Vérifiez avec /memory que la correction a bien été enregistrée en auto‑mémoire, confirmez le chargement avec /context, puis lancez /doctor pour voir s'il propose d'alléger votre CLAUDE.md.

Quiz éclair

Combien de types de notes l'auto‑mémoire de Claude Code enregistre‑t‑elle ?

✓ Exact. 4 types : user (préférences), feedback (corrections confirmées), project (contexte non déductible du code), reference (où trouver une info externe).
✗ Pas tout à fait. La réponse est 4 : user, feedback, project, reference.
03

Commandes & Skills — industrialiser ses prompts

D'un prompt improvisé à une procédure versionnée

Le vibe‑coding, c'est retaper le même prompt de mémoire, avec les variations que ça implique. Une skill fige ce prompt dans un fichier SKILL.md versionné : reproductible, partageable par git, auditable via son allowed-tools.

Ce qu'il faut retenir

Exercice pratique

Créez .claude/skills/resume-diff/SKILL.md avec un frontmatter minimal (description, disable-model-invocation: true) et un corps qui injecte !git diff HEAD puis demande un résumé en 3 puces. Testez avec /resume-diff, puis ajoutez context: fork et agent: Explore pour le faire tourner en sous‑agent en arrière‑plan.

Quiz éclair

Où placer une commande qui doit aussi embarquer des fichiers annexes (scripts, docs de référence) ?

✓ Exact. Un dossier .claude/skills/nom/SKILL.md peut embarquer des fichiers de support en plus du prompt, contrairement à un simple fichier .claude/commands/nom.md.
✗ Pas tout à fait. C'est .claude/skills/nom/SKILL.md : le mécanisme successeur des commandes slash, qui peut embarquer des fichiers annexes.
04

Plan Mode & réflexion étendue

Réfléchir avant d'agir, régler la profondeur

En vibe‑coding, on espère que ça marche sans visibilité sur ce que l'IA va faire. Le mode plan force une phase de recherche avant toute modification, et le niveau d'effort rend le raisonnement du modèle explicite et réglable — la base d'une pratique reproductible.

Ce qu'il faut retenir

Exercice pratique

Lancez claude --permission-mode plan, puis demandez : « ultrathink: propose une architecture pour ajouter du rate‑limiting à cette API ». Observez le plan, approuvez avec « Yes, and use auto mode ». Dans une nouvelle session, comparez /effort low vs /effort xhigh sur la même question pour sentir la différence de profondeur.

Quiz éclair

Lequel de ces mots‑clés déclenche encore un raisonnement plus profond pour un seul tour ?

✓ Exact. Seul « ultrathink » est encore reconnu comme spécial aujourd'hui. « think », « think hard » et « think more » sont transmis comme texte ordinaire — un piège classique pour qui a appris Claude Code il y a plus d'un an.
✗ Pas tout à fait. C'est « ultrathink » : les autres mots‑clés historiques ne sont plus reconnus comme spéciaux.
05

Sous‑agents — déléguer et paralléliser

L'outil Agent (ex‑Task)

Le vibe‑coding, c'est un seul fil où tout se mélange : recherche, écriture, tests, contexte qui explose. Les sous‑agents isolent chaque tâche (contexte séparé, outils restreints, parfois un worktree dédié) et laissent choisir consciemment quel modèle fait quoi.

Ce qu'il faut retenir

Exercice pratique

Demandez à Claude de créer un sous‑agent code-reviewer en lecture seule (Read, Grep, Glob), modèle haiku. Lancez /subtask avec cet agent et observez son exécution en arrière‑plan via /tasks. Ajoutez ensuite isolation: worktree pour qu'il travaille dans une copie git isolée, puis bloquez‑le avec une règle permissions.deny: ["Agent(code-reviewer)"].

Quiz éclair

Comment reprendre aujourd'hui un sous‑agent déjà lancé ?

✓ Exact. L'outil Agent n'accepte plus de paramètre resume depuis la v2.1.77 : on cible le sous‑agent existant via SendMessage({to: agentId}).
✗ Pas tout à fait. C'est SendMessage({to: agentId}) ; le paramètre resume de l'outil Agent a été retiré.
06

Hooks — automatiser sans dépendre du modèle

Des règles déterministes, pas des espoirs

En vibe‑coding, on laisse le modèle décider seul quand formatter, tester ou demander une confirmation — et il oublie parfois. Les hooks transforment ces habitudes en règles qui s'exécutent toujours au bon moment, scriptables et partageables en équipe.

Ce qu'il faut retenir

Exercice pratique

Créez un hook PreToolUse sur Bash avec if: "Bash(rm *)" qui bloque (code de sortie 2) toute commande rm. Ajoutez un hook PostToolUse sur Edit|Write avec continueOnBlock: true qui lance un linter et renvoie l'erreur à Claude au lieu d'arrêter le tour. Inspectez /hooks pour voir la provenance de chaque hook actif.

Quiz éclair

Que fait continueOnBlock: true sur un hook PostToolUse ?

✓ Exact. Un typecheck qui échoue peut ainsi être corrigé automatiquement par Claude, au lieu d'interrompre la session.
✗ Pas tout à fait. Il renvoie la raison du blocage à Claude comme résultat d'outil, ce qui lui permet de corriger et continuer au lieu de s'arrêter.
07

MCP — connecter des outils externes en sécurité

Model Context Protocol

En vibe‑coding, on branche des outils MCP au hasard sans savoir qui les a approuvés ni ce qu'ils peuvent lire. Passer pro, c'est maîtriser les scopes (.mcp.json versionné), les approbations et les allowlists/denylists.

Ce qu'il faut retenir

Exercice pratique

Créez un .mcp.json à la racine avec un serveur MCP HTTP public, lancez claude, observez l'invite « Pending approval », acceptez‑la puis vérifiez avec claude mcp list. Bloquez ensuite ce même serveur pour vous via deniedMcpServers dans ~/.claude/settings.json.

Quiz éclair

Quel statut affiche un serveur MCP de portée projet non approuvé dans .mcp.json ?

✓ Exact. Jamais d'auto‑approbation silencieuse : claude mcp list affiche le statut d'approbation de chaque serveur configuré.
✗ Pas tout à fait. C'est « Pending approval » : un serveur MCP de portée projet non approuvé ne se connecte jamais silencieusement.
08

Checkpoints & Rewind — le filet de sécurité

Explorer sans crainte

Le vibe‑coding enchaîne des prompts à l'aveugle sans filet si Claude part dans la mauvaise direction. Les checkpoints transforment cette improvisation en pratique pro : chaque prompt devient un point restaurable, code et/ou conversation, avant même un commit Git.

Ce qu'il faut retenir

Exercice pratique

Faites implémenter une fonctionnalité simple, laissez Claude modifier 2‑3 fichiers, puis demandez volontairement une modification que vous jugez mauvaise. Appuyez deux fois sur Échap (ou /rewind), choisissez le point juste avant, testez « Restore code and conversation » puis, sur un autre essai, « Restore code » seul.

Quiz éclair

Depuis la v2.1.216, quels fichiers /rewind ignore‑t‑il lors d'une restauration de code ?

✓ Exact. Ces fichiers gardent leur contenu actuel, avec un message « Restored the code, but skipped N files » — utile à savoir pour les dotfiles liés symboliquement.
✗ Pas tout à fait. Ce sont les liens symboliques et liens physiques (hard links) qui sont ignorés, pas les fichiers .env ou binaires.
09

Git, worktrees & automatisation PR

Travailler à plusieurs sans collision

Le vibe‑coding s'arrête là où le code touche un dépôt partagé : sans worktrees ni discipline Git, on écrase le travail des autres ou on pousse des commits non relus. Les worktrees et l'automatisation PR font tourner plusieurs agents en parallèle sans collision, avec une trace propre.

Ce qu'il faut retenir

Exercice pratique

Lancez claude --worktree essai-pro pour une session isolée. Modifiez un fichier, lancez /code-review high --fix avant de committer, puis /commit-push-pr. Vérifiez qu'un git push --force ne serait pas auto‑approuvé, et ajoutez worktree.baseRef: "head" dans .claude/settings.json.

Quiz éclair

Que se passe‑t‑il si vous demandez à /commit-push-pr un git push --force ?

✓ Exact. Depuis la v2.1.229, les flags dangereux (--force, --amend, --no-verify) ne sont plus auto‑approuvés par /commit-push-pr : le reste du workflow reste automatisé.
✗ Pas tout à fait. Il redemande confirmation : /commit-push-pr n'auto‑approuve plus les flags git/gh dangereux depuis la v2.1.229.
10

Arrière‑plan & workflows multi‑agents

Passer à l'échelle sans perdre le contrôle

En vibe‑coding, on lance un prompt sans savoir combien d'agents tournent ni comment les arrêter. Maîtriser les tâches en arrière‑plan et les workflows, c'est savoir exactement qui fait quoi, avec des garde‑fous de taille et de permissions inter‑sessions.

Ce qu'il faut retenir

Exercice pratique

Lancez claude --bg "audite les TODO du repo", ouvrez claude agents, épinglez la session (Ctrl+T), consultez ses logs avec claude logs <id>. Testez ensuite /goal tous les tests passent et le lint est propre sur une petite tâche pour voir Claude boucler seul jusqu'à la condition.

Quiz éclair

Combien d'agents un Workflow peut‑il faire tourner en concurrence, au maximum, par défaut ?

✓ Exact. 16 agents concurrents au maximum, pour un plafond total de 1000 agents sur toute l'exécution d'un workflow.
✗ Pas tout à fait. C'est 16 : au‑delà, les appels supplémentaires attendent en file qu'un emplacement se libère.
11

Plugins & marketplaces

Outiller toute l'équipe, pas juste soi

En vibe‑coding, on installe un plugin trouvé au hasard et on croise les doigts. En pro, les plugins et marketplaces donnent la reproductibilité (version épinglée par SHA), la sécurité (secrets jamais injectés en shell) et la gouvernance (activation explicite, coût en tokens visible).

Ce qu'il faut retenir

Exercice pratique

Lancez claude plugin init mon-plugin --with skills hooks. Ajoutez "defaultEnabled": false et vérifiez qu'il faut claude plugin enable mon-plugin pour l'activer. Exécutez claude plugin details mon-plugin pour voir son coût en tokens projeté par session.

Quiz éclair

Un plugin déclare defaultEnabled: false. Que doit faire l'utilisateur avant qu'il ne soit actif ?

✓ Exact. Une activation explicite est requise même une fois le plugin installé — une protection contre l'activation silencieuse.
✗ Pas tout à fait. Il faut lancer claude plugin enable <nom> : l'installation seule ne suffit pas à activer un plugin marqué defaultEnabled: false.
12

SDK, mode headless, CI/CD & IDE

Faire de Claude Code une brique d'infrastructure

Le vibe‑coding valide chaque action à l'instinct en mode interactif : ça ne passe pas à l'échelle. Le mode headless et le SDK transforment Claude Code en brique reproductible : scripts déterministes, garde‑fous explicites, sortie structurée exploitable en CI.

Ce qu'il faut retenir

Exercice pratique

Écrivez claude --bare -p "Résume les 3 derniers commits" --allowedTools "Bash(git log *)" --permission-mode auto --permission-prompts none --output-format json. Inspectez la sortie avec jq pour extraire .result et .total_cost_usd.

Quiz éclair

Quel flag saute la découverte automatique de hooks, skills, sous‑agents, plugins, MCP et CLAUDE.md ?

✓ Exact. C'est le mode recommandé pour tout appel scripté ou SDK : comportement prévisible, sans configuration locale implicite.
✗ Pas tout à fait. C'est --bare : il élimine toute découverte automatique de configuration locale pour un comportement scripté prévisible.
13

Épilogue — checklist du praticien & sources

Douze leviers, un seul objectif : ne plus jamais avoir à espérer. Voici la checklist qui résume ce cours — cochez‑la avant de dire qu'un projet Claude Code est « prêt pour la prod ».

Checklist du praticien pro

  • Le sandbox Bash et les règles réseau sont actifs sur tout projet touchant des secrets ou une prod.
  • .claude/settings.json (permissions, hooks) est versionné et revu comme du code.
  • CLAUDE.md documente les pièges et conventions non standard — pas ce que Claude peut déjà déduire du code.
  • Les tâches répétées vivent dans des skills versionnées, pas dans la mémoire de qui tape le prompt.
  • Les tâches risquées passent par le mode plan avant toute exécution.
  • Les sous‑agents ont un périmètre d'outils explicite (tools:/disallowedTools:), pas un accès total par défaut.
  • Les vérifications critiques (lint, tests, secrets) sont des hooks, pas des espoirs.
  • Chaque serveur MCP externe est passé en revue avant approbation, avec une allowlist en équipe.
  • /rewind et les worktrees sont réflexes avant toute expérimentation risquée sur du code partagé.
  • Les workflows multi‑agents ont une workflowSizeGuideline assumée, pas « laisser tourner et voir ».
  • Les plugins installés sont épinglés par SHA et leur coût en tokens est connu (claude plugin details).
  • Les intégrations CI utilisent --bare, une sortie --output-format json et des permissions explicites — jamais un --dangerously-skip-permissions dans un pipeline partagé.
