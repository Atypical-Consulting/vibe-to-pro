MCP (conectar herramientas externas con seguridad)

Model Context Protocol

En vibe-coding, conectamos herramientas MCP al azar sin saber quién las aprobó ni qué pueden leer. Pasar a profesional es dominar los scopes (.mcp.json versionado), las aprobaciones y las allowlists/denylists.

Prueba de nivel

¿Qué estado muestra un servidor MCP de ámbito de proyecto no aprobado en .mcp.json?

✓ Correcto. Nunca hay aprobación automática silenciosa: claude mcp list muestra el estado de aprobación de cada servidor configurado.
→ Ya dominas esta palanca, pasa al módulo siguiente
✗ No exactamente. Es «Pending approval»: un servidor MCP de ámbito de proyecto no aprobado nunca se conecta en silencio.

Quién ha aprobado realmente esta herramienta MCP conectada a tu proyecto?

Seguramente ya has conectado un servidor MCP pegando un comando encontrado en algún sitio, sin saber muy bien qué podía hacer una vez conectado. Se lanza, las herramientas aparecen y seguimos adelante, hasta el día en que nos preguntamos: ¿a qué datos tiene realmente acceso esa cosa, y quién validó que pudiera conectarse a ellos? Un servidor MCP (siglas de Model Context Protocol) no es un simple script local: es una pasarela hacia una herramienta o un servicio externo, con sus propias credenciales y sus propios permisos. Entender cómo Claude Code regula esta pasarela es la diferencia entre una configuración que «funciona en tu máquina» por casualidad y una configuración que se puede compartir, auditar y en la que el equipo puede confiar.

El mecanismo se basa antes que nada en una cuestión de ámbito, o scope: un servidor MCP puede declararse en local (solo para ti, en este proyecto), en user (en todos los sitios donde trabajes), o en project. Este último scope es el más útil en equipo, porque vive en un archivo .mcp.json que se commitea con el resto del código: cualquiera que clone el repositorio recupera automáticamente la misma lista de servidores MCP, sin tener que reconfigurarla a mano. Pero compartir una configuración en Git no significa ejecutarla sin mirar, y precisamente ahí es donde Claude Code coloca una salvaguarda.

¿Qué ocurre, en concreto, la primera vez que abres un proyecto que contiene un .mcp.json añadido por otra persona? Claude Code nunca conecta en silencio un servidor de ámbito project hasta que ha sido aprobado: queda mostrado como Pending approval (en espera de aprobación), un estado que también puedes consultar en cualquier momento con claude mcp list. Esta regla (nunca hay aprobación automática) protege contra un escenario simple pero real: un archivo de configuración deslizado en un repositorio, que conectaría discretamente una herramienta a tus archivos o a tus credenciales desde el primer arranque.

Una vez aprobado un servidor, sigues teniendo el control individual gracias a las listas allowedMcpServers y deniedMcpServers. Identifican un servidor por su nombre, su URL o su comando (con comodines), incluso para servidores desplegados a escala de empresa. El protocolo también regula cómo circulan los datos con el servidor: el transporte HTTP streamable es hoy el recomendado, mientras que el antiguo SSE sigue siendo compatible pero está explícitamente marcado como obsoleto en la documentación. Dicho de otro modo, asegurar una herramienta MCP no consiste solo en decidir si tiene permiso para conectarse, sino también en cómo lo hace. A continuación, en detalle, lo que esto cambia en la práctica.

Ejercicio práctico

Crea un .mcp.json en la raíz con un servidor MCP HTTP público, y luego lanza claude. Observa el aviso «Pending approval», acéptalo, y luego comprueba con claude mcp list. Después, bloquea ese mismo servidor para ti mediante deniedMcpServers en ~/.claude/settings.json.

Solución & verificación

Crear un .mcp.json en la raíz coloca el servidor en ámbito project : es este archivo, commiteado, el que permite compartir la configuración en equipo vía Git, pero cualquier entrada aún no aprobada se muestra como «Pending approval» en lugar de conectarse en silencio (nunca hay aprobación automática). Una vez aprobado por parte del equipo, el bloqueo individual pasa por deniedMcpServers en ~/.claude/settings.json, que hace coincidir el servidor por serverName, serverUrl o serverCommand :

{ "deniedMcpServers": [{"serverName": "nom-du-serveur"}] }
  • Al lanzar claude, aparece el mensaje exacto «Pending approval» para el servidor del .mcp.json antes de cualquier intento de conexión.
  • Tras la aceptación, claude mcp list muestra este servidor con un estado de aprobación pasado a aprobado (en lugar de Pending).
  • Tras añadir la entrada deniedMcpServers y relanzar claude, ese mismo servidor ya no aparece como disponible/conectado para ti (sus herramientas ya no se ofrecen), aunque sigue activo para el resto del equipo.
