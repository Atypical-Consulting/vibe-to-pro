Hooks: automatizar sin depender del modelo

Reglas deterministas, no esperanzas

En el vibe-coding, dejamos que el modelo decida solo cuándo formatear, probar o pedir confirmación, y a veces se olvida. Los hooks convierten esos hábitos en reglas que se ejecutan siempre en el momento preciso, programables y compartibles en equipo.

¿Y si las buenas prácticas se ejecutaran solas, sin que tuvieras que volver a pedirlas?

En el vibe-coding, todos hemos vivido esto: le pedimos a Claude que ejecute las pruebas antes de hacer commit, o que formatee el código correctamente. Nueve de cada diez veces lo hace. Luego, un día, se le olvida, ocupado respondiendo a otra cosa. Nada anormal: en cada paso, el modelo decide por sí mismo qué hacer, y una decisión, aunque sea acertada en la inmensa mayoría de los casos, sigue siendo una decisión, no una garantía. Un hook cambia completamente las reglas del juego: es una regla que escribes una vez y que se ejecuta automáticamente cada vez que ocurre un evento concreto en la sesión, piense en ello el modelo o no.

En concreto, ¿cómo funciona? Un hook se engancha a un evento del ciclo de vida de Claude Code (justo antes de que se ejecute una herramienta, justo después, antes de una compactación del contexto que resume la conversación para liberar espacio, y muchos otros) y dispara en ese momento preciso una acción que tú defines: ejecutar un script local (type: "command"), llamar directamente a una herramienta MCP ya instalada interpolando los campos del evento (type: "mcp_tool"), o enviar el JSON del evento mediante POST a un servicio externo y esperar su respuesta (type: "http"). Incluso puedes definir con mucha precisión cuándo se dispara el hook, gracias a un campo if que reutiliza la sintaxis de las reglas de permisos, por ejemplo reaccionar solo a los comandos git con algo como Bash(git *). El hook no le pide nada al modelo: se ejecuta, punto final, lo que lo convierte en una red de seguridad determinista en lugar de una esperanza.

Pero un hook no es necesariamente una barrera que lo detiene todo en seco. Ahí es donde se pone interesante: en un hook PostToolUse (el que se dispara justo después de usar una herramienta), la opción continueOnBlock: true permite devolver el motivo de un bloqueo a Claude como un simple resultado de herramienta, en lugar de interrumpir bruscamente el turno. Un typecheck que falla, por ejemplo, puede así ser corregido automáticamente por Claude sobre la marcha, sin que tengas que relanzar nada tú mismo. En el otro extremo de la sesión, un hook PreCompact puede directamente impedir que se produzca una compactación (devolviendo un código de salida 2), el tiempo necesario para archivar lo importante antes de que el historial se resuma.

Y como estas reglas pueden vivir en un archivo de configuración compartido por todo el equipo, o incluso limitarse al ciclo de vida de un skill o un agente concreto mediante su frontmatter, todo el mundo trabaja con las mismas barreras de protección, sin tener que repetir las mismas instrucciones en cada sesión. A continuación, en detalle, lo que esto cambia en la práctica.

Quiz rápido

Según la documentación de los hooks, ¿qué evento se dispara justo antes de una compactación del contexto y puede bloquearla con un código de salida 2?

✓ Correcto. PreCompact se dispara justo antes de una compactación y puede bloquearla (código de salida 2). PostCompact, en cambio, se dispara solo justo después, lo cual es útil, por ejemplo, para archivar información importante antes de que se compacte.
✗ No exactamente. Es PreCompact: interviene antes de la compactación y puede bloquearla con un código de salida 2. PostCompact se dispara después, una vez que la compactación ya se ha efectuado, por lo que es demasiado tarde para impedirla.
Quiz rápido

¿Qué tipo de hook permite llamar directamente a una herramienta MCP ya instalada, con interpolación de los campos de la entrada JSON del hook?

✓ Correcto. El tipo mcp_tool llama directamente a una herramienta MCP ya instalada, con interpolación de los campos de la entrada JSON del hook. Es útil, por ejemplo, para delegar una verificación de seguridad a una herramienta MCP existente, sin reescribir ningún script shell.
✗ No exactamente. Es el tipo mcp_tool: permite llamar directamente a una herramienta MCP ya instalada, interpolando los campos de la entrada JSON del hook, en lugar de ejecutar un script (command) o enviar una petición de red (http).
Ejercicio práctico

Crea un hook PreToolUse en Bash con if: "Bash(rm *)" que bloquee (código de salida 2) cualquier comando rm. Añade un hook PostToolUse en Edit|Write con continueOnBlock: true que ejecute un linter y devuelva el error a Claude en lugar de detener el turno. Inspecciona /hooks para ver la procedencia de cada hook activo.

Solución & verificación

El primer hook se apoya en el campo if, que acepta la sintaxis de las reglas de permisos (por ejemplo Bash(git *)) para dirigirse con precisión a un subcomando. Con if: "Bash(rm *)", el hook PreToolUse solo se dispara en los comandos rm, y un script que termina con código de salida 2 bloquea la llamada a la herramienta. El segundo hook aprovecha la opción continueOnBlock: true en PostToolUse, que devuelve el motivo del bloqueo a Claude como resultado de herramienta en lugar de detener el turno. Un linter que falla puede así ser corregido automáticamente por Claude en lugar de interrumpir la sesión. La configuración final esperada consta, por tanto, de dos entradas en la configuración de los hooks: una en PreToolUse (matcher Bash, if: "Bash(rm *)", comando que sale con código 2) y otra en PostToolUse (matcher Edit|Write, continueOnBlock: true, comando que ejecuta el linter).

  • Un comando rm que Claude intenta ejecutar se rechaza de inmediato: la herramienta Bash no se ejecuta y el mensaje de error devuelto por el hook (código de salida 2) aparece como resultado de herramienta en la conversación.
  • Tras una modificación mediante Edit o Write que rompe el linter, el turno no se detiene: el error del linter aparece como resultado de herramienta y Claude propone una corrección en el siguiente mensaje, en lugar de que la sesión se interrumpa.
  • El comando /hooks efectivamente lista los dos hooks como activos, con su procedencia (el archivo de settings donde se declaran) y sus respectivos matchers: Bash para el hook PreToolUse, Edit|Write para el hook PostToolUse.
