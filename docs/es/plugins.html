Plugins & marketplaces

Equipar a todo el equipo, no solo a uno mismo

En vibe-coding, se instala un plugin encontrado al azar y se cruzan los dedos. En modo profesional, los plugins y las marketplaces aportan reproducibilidad (versión fijada por SHA), seguridad (los secretos nunca se inyectan en el shell) y gobernanza (activación explícita, costo en tokens visible).

Prueba de nivel

Un plugin declara defaultEnabled: false. ¿Qué debe hacer el usuario antes de que esté activo?

✓ Correcto. Se requiere una activación explícita incluso una vez instalado el plugin: es una protección contra la activación silenciosa.
→ Ya dominas esta palanca, pasa al siguiente módulo
✗ No exactamente. Hay que ejecutar claude plugin enable <nom>: la instalación por sí sola no basta para activar un plugin marcado defaultEnabled: false.

Un plugin encontrado en GitHub, lo instalas… y luego?

Un plugin resulta tentador alguien lo programó, tú lo instalas y Claude Code sabe de repente hacer algo más. En vibe-coding, a menudo eso es todo lo que se pide. Funciona, así que se sigue adelante. Pero un plugin no es solo un comando más: puede aportar agentes, hooks (scripts que se disparan automáticamente en ciertos momentos) e incluso servidores MCP o LSP completos (LSP, por Language Server Protocol, el protocolo que le da a un editor una comprensión fina de un lenguaje de programación), todo ello empaquetado y distribuido mediante una marketplace, una especie de catálogo compartido. Y ahí es donde se vuelve interesante para un equipo: al declarar esta marketplace una sola vez en .claude/settings.json mediante extraKnownMarketplaces, todos acceden a ella sin tener que reinstalar nada por su cuenta.

Pero instalar un plugin no significa activarlo, y es una decisión de diseño deliberada. Si su autor puso defaultEnabled: false en el plugin.jsonel plugin permanece inerte hasta que tú mismo ejecutes claude plugin enable <nom>. ¿Por qué este paso que parece redundante? Porque un plugin que se activara solo al instalarse actuaría sobre tu proyecto antes incluso de que hayas decidido confiar en él. Y antes de dar ese paso, puedes consultar claude plugin details <nom>: el comando lista lo que trae el plugin y proyecta el costo en tokens que añadirá a cada sesión. Así sabes qué estás activando antes de activarlo, no después.

Queda un problema clásico: un plugin que apunta a una rama de GitHub puede cambiar bajo tus pies, ya que un commit subido la semana que viene no es el mismo que probaste hoy. Por eso marketplace.json puede fijar un sha, un commit git completo, como una foto fija en lugar de un flujo que sigue moviéndose. Misma lógica cuando el plugin ni siquiera está en git: una fuente de tipo archive instala directamente un zip vía HTTPS, sin git ni npm, también con un hash SHA-256 opcional para garantizar que el contenido recibido es exactamente el esperado. Resultado: lo que probaste es, hasta el commit exacto, lo mismo que se ejecutará en la máquina de tu colega o en CI.

Queda la cuestión de la confianza en cuanto a configuración y seguridad. ¿Podría un repositorio clonado colar discretamente sus propios ajustes de plugins en tu sesión? No: pluginConfigs ya no se lee desde los settings de proyecto, solo cuentan tus settings de usuario, --settings o los settings gestionados por tu organización. Es el comando /plugin el que los escribe, en tu ~/.claude/settings.json propio. Misma vigilancia del lado de los hooks de un plugin: la sustitución ${user_config.*} en forma shell está bloqueada, porque abriría una brecha de inyección si un valor de configuración contuviera código malicioso; hay que pasar por la forma exec o leer la variable de entorno $CLAUDE_PLUGIN_OPTION_<CLE>. Esto es, en detalle, lo que cambia concretamente.

Ejercicio práctico

Ejecuta el siguiente comando:

claude plugin init mon-plugin --with skills hooks

Añade "defaultEnabled": false en el plugin.json generado, y luego comprueba que hay que ejecutar el siguiente comando para activarlo:

claude plugin enable mon-plugin

Por último, ejecuta este comando para ver su costo en tokens proyectado por sesión:

claude plugin details mon-plugin
Solución & verificación

El plugin.json generado por claude plugin init no activa nada por sí solo. En cuanto añades "defaultEnabled": false, la referencia de los plugins exige una activación explícita antes de que el plugin esté activo, incluso una vez instalado. Por eso claude plugin enable mon-plugin se convierte en un paso obligatorio y no opcional. Una vez activado el plugin, claude plugin details mon-plugin lista sus componentes declarados (aquí los skills y hooks solicitados mediante --with skills hooks) y proyecta su costo en tokens por sesión incluso antes de que tengas que usarlos, lo que permite juzgar su huella sin dejarlo funcionar a ciegas.

  • Antes de claude plugin enable, un comando/skill del plugin invocado en la sesión falla o permanece invisible, y claude plugin list (o /plugin en el REPL) muestra mon-plugin con un estado desactivado.
  • claude plugin enable mon-plugin finaliza con un código de salida 0 y hace que mon-plugin pase al estado activo en claude plugin list.
  • claude plugin details mon-plugin muestra una estimación numérica del costo en tokens por sesión (un valor numérico), además de la lista de skills y hooks declarados, no solo los nombres de los componentes.
