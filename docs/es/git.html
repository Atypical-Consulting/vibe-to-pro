Git, worktrees & automatización de PR

Trabajar en paralelo sin colisiones

El vibe-coding se detiene donde el código toca un repositorio compartido: sin worktrees ni disciplina Git, se sobrescribe el trabajo de otros o se hace push de commits sin revisar. Los worktrees y la automatización de PR permiten ejecutar varios agentes en paralelo sin colisiones, con un historial limpio.

Varios agentes, un solo repositorio: cómo evitar el choque?

Seguramente ya lanzó Claude Code en una tarea y luego abrió una segunda ventana para que corrigiera otra cosa mientras la primera todavía se ejecutaba. Y ahí fue donde se atascó las dos sesiones modificaban los mismos archivos en la misma rama, y una terminó sobrescribiendo el trabajo de la otra. No es un error, es la consecuencia lógica de un repositorio Git clásico una sola copia de trabajo en el disco, así que solo un agente a la vez puede tocarla sin riesgo. Entonces, ¿cómo hacer que varios agentes se ejecuten en paralelo sobre el mismo proyecto, sin jugar a las sillas musicales con las ramas?

La respuesta está en una herramienta de Git ya presente pero a menudo ignorada: el worktree. Un worktree es una segunda copia de trabajo del mismo repositorio, ubicada en otra carpeta, pero que comparte el mismo historial de Git: no es un clon completo, solo una rama independiente que se puede modificar sin tocar la rama principal. Claude Code se apoya directamente en esto: el flag --worktree (o -w) crea esa carpeta aislada bajo .claude/worktrees/<nom>/, en una nueva rama llamada worktree-<nom>, de modo que un agente lanzado ahí dentro simplemente no puede sobrescribir lo que hace otro agente en otro lugar. Queda una pregunta: ¿desde dónde arranca este nuevo trabajo? Por defecto, parte deorigin/<branche par défaut> (una base limpia y actualizada), pero si ya tiene trabajo local sin subir que quiere continuar, hay que activar explícitamente la opción que parte de su HEAD local en su lugar.

El segundo punto de fricción del vibe-coding es el final de la tarea: una vez escrito el código, todavía hay que hacer commit, push, abrir una pull request (una solicitud de fusión hacia la rama principal, normalmente revisada antes de aceptarse). Y es precisamente ahí donde se salta un paso, o se hace push directo a la rama principal por reflejo. Claude Code automatiza esta mecánica: un agente que trabaja en segundo plano dentro de un worktree hace commit y push de su trabajo antes de terminar, y solo abre una pull request en borrador cuando la tarea lo justifica, respetando de paso las instrucciones de Git que dejó en su CLAUDE.md. Pero automatizar no significa dejar hacer todo sin supervisión: en este workflow de commit, push y pull request, los flags que podrían causar daños difíciles de deshacer (un push forzado, un commit modificado, un hook de verificación evitado) ya no se ejecutan automáticamente, vuelven a pedir una confirmación explícita. En otras palabras, la automatización le quita la tarea repetitiva, no la última palabra sobre las acciones arriesgadas.

Un último detalle cambia mucho el día a día: todos los worktrees de un mismo repositorio comparten la misma configuración (CLAUDE.md, ajustes de permisos, agentes personalizados, skills, memoria automática), así que no hace falta duplicar todo en cada nuevo frente paralelo. Y para mantener una vista general sin volver a abrir GitHub cada vez, el estado de la pull request asociada a su rama actual se muestra como un simple punto de color en la interfaz. Esto es, en detalle, lo que cambia en la práctica.

Ejercicio práctico

Ejecute el siguiente comando para iniciar una sesión aislada:

claude --worktree essai-pro

Modifique un archivo y luego ejecute /code-review high --fix antes de hacer commit, y por último /commit-push-pr. Compruebe que un git push --force no se auto-aprobaría, y agregue worktree.baseRef: "head" en .claude/settings.json.

Solución & verificación

claude --worktree essai-pro crea un worktree aislado bajo .claude/worktrees/essai-pro/, en una nueva rama worktree-essai-pro, lo que permite modificar un archivo sin tocar la rama de trabajo actual. Una vez que el archivo está commiteado, /commit-push-pr sube el trabajo y abre la PR. Desde la v2.1.229, ya no se ejecuta silenciosamente para un flag peligroso: un git push --force vuelve a pedir confirmación en lugar de auto-aprobarse. Para que este worktree (y los siguientes) arranquen desde el HEAD local, incluidos los commits sin subir, en lugar de desde origin/<branche par défaut>, hay que agregar explícitamente la siguiente configuración en .claude/settings.json:

{
  "worktree": { "baseRef": "head" }
}

Este es el ajuste final esperado por el ejercicio.

  • El directorio .claude/worktrees/essai-pro/ existe y, dentro de él, git branch --show-current devuelve worktree-essai-pro.
  • Al intentar un git push --force en este worktree mediante /commit-push-pr, aparece una confirmación explícita en lugar de un push ejecutado directamente.
  • .claude/settings.json contiene la clave "worktree": { "baseRef": "head" } después de la edición, y un nuevo worktree creado a continuación tiene el mismo commit de cabeza que la rama local actual (y no el de origin/<branche par défaut>).
