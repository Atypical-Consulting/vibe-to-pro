Subagentes, delegar y paralelizar

La herramienta Agent (antes Task)

El vibe-coding es un solo hilo donde todo se mezcla: investigación, escritura, pruebas, un contexto que se dispara. Los subagentes aíslan cada tarea (contexto separado, herramientas restringidas, a veces un worktree dedicado) y permiten elegir conscientemente qué modelo hace cada cosa.

¿Y si pudieras delegar sin perder el hilo?

Conoces ese momento en el que una sesión de Claude Code se dispersa en todas direcciones: le pides que busque un bug, luego que escriba una corrección, luego que ejecute las pruebas, luego que revise un archivo completamente distinto. En determinado momento, el contexto (todo lo que el modelo «recuerda» de la conversación) está tan cargado que las respuestas se vuelven menos precisas. Este es el síntoma clásico del vibe-coding: un único hilo de conversación que intenta cargar con todo a la vez. La solución no es hacerlo todo más rápido en ese mismo hilo, sino dividirlo: encargar cada tarea a un subagente separado, con su propio contexto, que no viene a contaminar el tuyo.

En concreto, este mecanismo de delegación se apoya en una herramienta que Claude Code llama Agent (se llamaba Task originalmente). Por defecto, un subagente hereda todas las herramientas disponibles (incluida la escritura de archivos y la ejecución de comandos Bash), salvo que lo restrinjas explícitamente con tools: o disallowedTools: en su frontmatter (el encabezado de configuración en la parte superior del archivo que define el agente). Esto es lo que permite crear, por ejemplo, un agente de revisión de código estrictamente de solo lectura: técnicamente no podrá romper nada, aunque lo intente. Puedes llevar el aislamiento todavía más lejos con isolation: worktree, que hace que el subagente trabaje en una copia git aparte, creada a partir de tu rama por defecto y eliminada automáticamente si no contiene ninguna modificación. Así puedes experimentar sin tocar nunca tu repositorio principal.

¿Pero por qué detenerse en un solo subagente a la vez? Ahí es donde entra la paralelización. /subtask lanza un subagente que permanece vinculado a tu sesión actual, visible en la lista de tareas; /fork, por su parte, duplica toda la conversación en una nueva sesión en segundo plano totalmente independiente, útil para probar un enfoque arriesgado sin bloquear tu trabajo. Este forking está activo por defecto en cuanto estás en una sesión interactiva. Para evitar que una escalada de delegaciones se vuelva incontrolable, existen dos salvaguardas: un límite de 20 subagentes ejecutados en paralelo (ajustable mediante la variable de entorno CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS, y sin límite total para el conjunto de una sesión), y una profundidad de anidamiento limitada a 3 niveles. Más allá de eso, la herramienta Agent desaparece para todos los subagentes salvo los forks, para evitar que un subagente lance indefinidamente otros subagentes.

Queda una pregunta: qué modelo hace funcionar cada subagente? No estás obligado a confiarlo todo al modelo más potente (y más costoso). El orden de resolución va del parámetro pasado en la invocación, al campo model: del frontmatter del agente (que también puede simplemente decir inherit para retomar el de la conversación), a la variable CLAUDE_CODE_SUBAGENT_MODEL, hasta el modelo de la conversación principal como último recurso: así puedes asignar conscientemente un modelo ligero a una tarea simple y reservar la potencia para lo que la merece. Un campo memory: incluso permite darle a un subagente una memoria persistente de una ejecución a otra, a nivel de usuario, de proyecto (el alcance recomendado, porque se puede versionar junto con el código) o de equipo local. Y para crear uno de estos subagentes, ya no hace falta un asistente dedicado: basta con pedírselo a Claude en lenguaje natural, o editar directamente un archivo en .claude/agents/. A continuación, en detalle, lo que esto cambia en la práctica.

Ejercicio práctico

Pide a Claude que cree un subagente code-reviewer de solo lectura (Read, Grep, Glob), modelo haiku. Lanza /subtask con este agente y observa su ejecución en segundo plano mediante /tasks. Añade después isolation: worktree para que trabaje en una copia git aislada, y luego bloquéalo con una regla permissions.deny: ["Agent(code-reviewer)"].

Solución & verificación

La restricción a las herramientas Read, Grep, Glob funciona porque el subagente recibe por defecto todas las herramientas disponibles, escritura y Bash incluidos, salvo restricción explícita mediante el campo tools: o disallowedTools: del frontmatter. Es esa misma declaración tools: Read, Grep, Glob la que lo hace estrictamente de solo lectura. Añadir isolation: worktree después hace que se ejecute en una copia git aislada, creada a partir de la rama por defecto y limpiada automáticamente si no se hizo ninguna modificación, sin tocar el repositorio principal. El ejercicio termina con una regla de permisos que bloquea explícitamente este subagente, del tipo permissions.deny: ["Agent(code-reviewer)"] en los settings.

  • En /tasks, la entrada del subagente code-reviewer pasa de «Working» a «Completed» sin que aparezca ninguna llamada a Edit, Write o Bash en su transcript de herramientas (solo figuran Read, Grep, Glob).
  • Una vez añadido isolation: worktree, aparece un nuevo worktree durante la ejecución (visible mediante git worktree list) y luego desaparece solo al final si no se modificó ningún archivo.
  • Después de añadir la regla permissions.deny: ["Agent(code-reviewer)"], cualquier nuevo intento de invocar este subagente concreto es rechazado explícitamente mediante un mensaje de permiso bloqueado, en lugar de ejecutarse como antes.
