SDK, modo headless, CI/CD & IDE

Convertir Claude Code en un componente de infraestructura

El vibe-coding valida cada acción por instinto en modo interactivo , y eso no escala. El modo headless y el SDK convierten Claude Code en un componente reproducible: scripts deterministas, barreras de seguridad explícitas, salida estructurada utilizable en CI.

Prueba de nivel

¿Qué flag omite el descubrimiento automático de hooks, skills, subagentes, plugins, MCP y CLAUDE.md?

✓ Correcto. Es el modo recomendado para cualquier llamada scripteada o del SDK: comportamiento predecible, sin configuración local implícita.
→ Ya dominas esta palanca, pasa al siguiente módulo
✗ No exactamente. Es --bare: elimina todo descubrimiento automático de configuración local para lograr un comportamiento scripteado predecible.

¿Y si no hubiera nadie para hacer clic en «Sí»?

En modo interactivo, todo es simple: ves lo que Claude Code está a punto de hacer, lo validas o lo corriges sobre la marcha. Pero ¿qué pasa cuando quieres conectar Claude Code a un pipeline CI/CD (el sistema que compila y prueba tu código automáticamente en cada envío) que se ejecuta a las 3 de la madrugada, sin nadie frente a la pantalla? O cuando quieres invocarlo desde tu propio programa, como una simple función? El modo interactivo, con sus mensajes de confirmación y su configuración local implícita, deja entonces de tener sentido: se necesita un comportamiento que permanezca idéntico en cada ejecución, sin sorpresas y sin depender de lo que haya en tu máquina.

Ese es precisamente el papel del modo headless (sin interfaz, controlado únicamente por la línea de comandos) y del flag --bare. --bare hace tabla rasa: omite todo descubrimiento automático de hooks, skills, subagentes, plugins, servidores MCP, memoria y archivo CLAUDE.md. El resultado: solo lo que pasas explícitamente en la línea de comandos determina el comportamiento de la sesión, lo que la hace reproducible de una máquina a otra. Combinado con --permission-prompts none, que convierte automáticamente en rechazo cualquier acción que normalmente habría disparado un mensaje de confirmación, obtienes un script que nunca se queda bloqueado esperando una respuesta humana que no llegará. El SDK, hoy renombrado Claude Agent SDK, formaliza la misma lógica del lado del código: en lugar de escribir un comando, tu programa controla directamente una sesión de Claude Code.

Pero un script sin supervisión también debe saber protegerse por sí mismo, en su propio lugar. El callback canUseTool del SDK ilustra bien esta lógica de capas: solo se llama si nada antes que él (un hook PreToolUse, una regla allow/deny/ask, el modo de permiso) ya ha decidido, lo que te permite añadir una validación de negocio a medida sin duplicar lo que ya existe. La misma lógica de prudencia se aplica del lado de la resiliencia: el mecanismo fallbackModel cambia automáticamente a un modelo de reserva en caso de sobrecarga o error del servidor, pero nunca en caso de error de autenticación, de facturación o de rate-limit. Cambiar de modelo no resolvería nada de esos problemas: es mejor que el job falle claramente en lugar de que oculte un incidente real. En cuanto a maxBudgetUsd, limita el gasto de una ejecución automatizada: nadie vigila el contador en tiempo real, así que es el propio parámetro el que debe cortar antes de que la factura se dispare.

Queda un último problema: ¿cómo sabe un pipeline, sin un humano que lea la pantalla, que todo salió bien? Produciendo una salida estructurada en lugar de un texto que haya que interpretar a simple vista. En --output-format stream-json, el mensaje system/init expone por ejemplo un campo plugin_errors que lista los errores de carga de plugin (ausente si no hay ninguno), lo que ofrece una puerta de validación simple de escribir en un script de CI. En el trabajo desde el teclado en lugar de en un pipeline, el mismo CLI se encuentra integrado en la extensión de VS Code (panel lateral, diffs en línea, menciones @ vinculadas a la selección), y /statusline te mantiene informado en tiempo real del modelo, el costo y el contexto utilizados. Esto es, en detalle, lo que cambia concretamente.

¿En qué caso el mecanismo fallbackModel del SDK nunca cambia a un modelo de reserva?

✓ Correcto. Correcto. fallbackModel acepta hasta tres modelos probados en orden, pero únicamente en caso de sobrecarga o error del servidor, nunca para un error de autenticación, de facturación o de rate-limit.
✗ No exactamente. No exactamente. La sobrecarga y el error del servidor sí activan un cambio de modelo; es justamente el error de autenticación, de facturación o de rate-limit el que nunca activa fallbackModel.
Quiz rápido

¿Qué significa la ausencia del campo plugin_errors en el mensaje system/init (con --output-format stream-json)?

✓ Correcto. Correcto. plugin_errors lista los errores de carga de plugin y no aparece si no hay ninguno, lo que permite una puerta de CI simple, por ejemplo jq -e '.plugin_errors // [] | length == 0'.
✗ No exactamente. No exactamente. Este campo no informa ni sobre el número de plugins instalados ni sobre --bare: su ausencia solo indica que no se produjo ningún error de carga de plugin.
Ejercicio práctico

Escribe el siguiente comando:

claude --bare -p "Résume les 3 derniers commits" --allowedTools "Bash(git log *)" --permission-mode auto --permission-prompts none --output-format json

Inspecciona la salida con jq para extraer .result y .total_cost_usd.

Solución & verificación

El comando funciona porque --bare elimina todo descubrimiento automático de hooks, skills, subagentes, plugins, MCP, memoria y CLAUDE.md: solo lo que se pasa explícitamente en la línea de comandos (aquí --allowedTools "Bash(git log *)") determina el comportamiento, lo que hace que la llamada sea reproducible para un script. Combinado con --permission-prompts none, que convierte automáticamente en rechazo cualquier acción que normalmente habría disparado un mensaje de confirmación, el job permanece no interactivo de principio a fin: cualquier comando fuera del perímetro git log es rechazado sin esperar una respuesta humana. --output-format json produce luego un único objeto JSON del cual jq extrae .result (el resumen) y .total_cost_usd (el costo de la llamada).

  • El comando termina con un código de salida 0 y muestra un único objeto JSON en stdout (no varias líneas, ya que el formato no es stream-json).
  • jq -r '.result' devuelve un texto no vacío que resume bien los últimos 3 commits, y jq '.total_cost_usd' devuelve un número decimal positivo (nunca null).
  • No aparece ningún mensaje de confirmación durante la ejecución; si se hubiera intentado un comando fuera del perímetro Bash(git log *) habría sido rechazado automáticamente en lugar de bloquear la terminal en espera de una validación.
