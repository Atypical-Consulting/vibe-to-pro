Contrôle & sécurité : permissions, sandbox, mode auto

La fondation avant tout le reste

Le vibe‑coding, c'est laisser un agent exécuter des commandes au fil de l'eau sans jamais se demander ce qu'il pourrait casser ou exfiltrer. Maîtriser les permissions et le sandbox, c'est définir précisément le périmètre : quels fichiers Claude peut lire, quels domaines réseau il peut joindre, quelles commandes destructrices restent bloquées par défaut. Cela forme un socle reproductible et auditable en équipe via .claude/settings.json.

→ Vous maîtrisez déjà ce levier, passer au module suivant
✗ Pas tout à fait. C'est git reset --hard qui est bloqué par défaut en mode auto, avec d'autres commandes destructrices, et non les commandes de lecture comme git status ou git commit.

Qui décide vraiment de ce que Claude Code a le droit de faire ?

Quand vous « vibe-codez », vous avez sans doute déjà ressenti ce petit vertige : l'agent propose une commande, vous validez sans trop réfléchir, et à un moment vous vous demandez ce qui se passerait s'il tapait git push --force ou fouillait un dossier que vous ne vouliez pas lui montrer. C'est exactement le problème que le mode auto essaie de résoudre. Depuis un certain temps, il est même devenu le mode de démarrage par défaut sur les plans Pro, Max et Team : vous lancez simplement claude, sans flag particulier, et la session démarre déjà dans ce mode. Shift+Tab permet de basculer vers un autre mode à tout moment. L'ancien mode « par défaut », lui, a d'ailleurs changé de nom : on l'appelle désormais « Manual » partout dans l'interface, précisément pour rappeler qu'il vous fait valider chaque action une par une.

Mais que bloque le mode auto, concrètement, pour mériter votre confiance ? Il ne vous demande pas de confirmer chaque commande, car ce serait fastidieux et vous finiriez par cliquer « oui » sans lire. À la place, il maintient une liste de commandes reconnues comme destructrices (git reset --hard, git clean -fd, git stash drop, terraform destroy, entre autres) et les bloque par défaut, sans que vous ayez rien configuré. Le principe est malin : ce blocage n'est pas définitif, il se lève au cas par cas si vous formulez l'intention explicitement (« force-push cette branche »), ce qui vous laisse la main sans vous obliger à tout surveiller en permanence. À l'autre extrémité du curseur, le mode bypass (--dangerously-skip-permissions) retire la plupart des garde-fous, y compris sur des chemins normalement protégés comme .claude/ ou .git/, mais un filet de sécurité sur les suppressions vraiment catastrophiques (rm -rf / ou ~) reste actif quoi qu'il arrive ; c'est un mode à réserver à des conteneurs ou VM isolés, jamais à votre machine de tous les jours. Et si vous voulez l'inverse (un périmètre volontairement rétréci pour ouvrir un dépôt inconnu ou faire découvrir l'outil à un débutant), le flag --restricted va plus loin encore : il retire les outils d'exécution de commandes et l'accès web, confine les outils fichiers au répertoire de travail, et refuse tout retour au mode bypass, sans possibilité de changer d'avis en cours de session.

Il y a ensuite une deuxième ligne de défense, plus basse dans la pile : le sandbox, littéralement un « bac à sable ». L'idée générale d'un sandbox est simple. Au lieu de faire confiance à un programme sur parole, on l'enferme dans un environnement cloisonné où il ne peut techniquement pas sortir d'un périmètre donné, même s'il essaie. Claude Code embarque un sandbox natif pour son outil Bash, qui s'appuie sur Seatbelt (le mécanisme de confinement intégré à macOS) et sur bubblewrap (son équivalent côté Linux) sous Linux ou WSL2. Windows natif, en revanche, n'est pas pris en charge : il faut passer par WSL2 pour en profiter. Vous l'activez simplement avec /sandbox en session, sans installation supplémentaire sur macOS. Ce sandbox confine les accès fichiers et réseau, mais il ne bloque aucun identifiant sensible par défaut : c'est à vous de déclarer des règles sandbox.credentials.files ou envVars pour refuser (deny) ou masquer (mode: "mask") un secret précis, et ces réglages doivent impérativement vivre dans ~/.claude/settings.json, vos settings personnels, car ils sont tout simplement ignorés s'ils se trouvent dans les settings de projet.

Reste la question de l'équipe : comment partager ces règles sans que chacun reparte de zéro ? Claude Code sépare deux fichiers : .claude/settings.json, versionné et partagé, pour les règles communes, et .claude/settings.local.json, personnel et gitignoré, pour vos préférences propres. Ces règles peuvent même utiliser des jokers dans les commandes Bash autorisées, comme Bash(npm *) ou Bash(git * main). Un piège classique : un motif aussi large que ce dernier autorise aussi git -c ..., qui peut exécuter un programme arbitraire. D'où l'intérêt de toujours vérifier ses règles avec --verbose avant de les déployer. Et même en mode auto, la première lecture d'un fichier situé hors du répertoire de travail déclenche une invite unique, qui vous laisse choisir d'autoriser définitivement, de bloquer, ou de redemander la prochaine fois. Voici, en détail, ce que ça change concrètement.

Exercice pratique

Créez (ou réutilisez) un dépôt d'entraînement : un dépôt jetable, jamais votre dépôt principal, que vous reprendrez au fil des modules suivants pour accumuler une vraie configuration .claude/. Dans ce dépôt : activez le sandbox avec /sandbox, choisissez le mode auto, puis demandez à Claude de lister ~/.ssh et de faire un git push --force. Observez le blocage réseau/lecture, puis ajoutez dans ~/.claude/settings.json un bloc sandbox.credentials.files avec mode: "deny" sur un fichier sensible, et vérifiez le résultat via l'onglet /sandbox → Config.

Solution & vérification

Le sandbox natif de Claude Code s'appuie sur Seatbelt (macOS) ou bubblewrap (Linux/WSL2) pour confiner réellement les accès fichiers et réseau de l'outil Bash : une fois activé via /sandbox, il bloque donc de lui-même la lecture de ~/.ssh et la connexion réseau du git push --force, sans configuration additionnelle. Ce mécanisme ne bloque en revanche aucun identifiant particulier par défaut : il faut ajouter explicitement une entrée sandbox.credentials.files avec mode: "deny" pour refuser l'accès à un fichier sensible précis, et ce réglage doit être écrit dans ~/.claude/settings.json (settings utilisateur), car ces clés sont ignorées si elles se trouvent dans les settings de projet.

  • La commande listant ~/.ssh échoue avec un message de refus émis par le sandbox (accès fichier hors périmètre autorisé) plutôt qu'un simple refus de permission Claude Code classique.
  • Le git push --force échoue côté réseau (connexion refusée ou hôte injoignable) au lieu d'aboutir ou de simplement demander confirmation.
  • Dans l'onglet /sandbox → Config, le fichier ciblé apparaît avec la règle deny appliquée uniquement s'il a été déclaré dans ~/.claude/settings.json ; la même entrée placée dans les settings de projet n'apparaît pas comme active.
