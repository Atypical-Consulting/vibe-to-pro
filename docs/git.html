Git, worktrees & automatisation PR

Travailler à plusieurs sans collision

Le vibe‑coding s'arrête là où le code touche un dépôt partagé : sans worktrees ni discipline Git, on écrase le travail des autres ou on pousse des commits non relus. Les worktrees et l'automatisation PR font tourner plusieurs agents en parallèle sans collision, avec une trace propre.

Plusieurs agents, un seul dépôt : comment éviter le carambolage ?

Vous avez sans doute déjà lancé Claude Code sur une tâche, puis ouvert une deuxième fenêtre pour lui faire corriger autre chose pendant que la première tournait encore. Et là, ça a coincé : les deux sessions modifiaient les mêmes fichiers sur la même branche, et l'une a fini par écraser le travail de l'autre. Ce n'est pas un bug, c'est la conséquence logique d'un dépôt Git classique : une seule copie de travail sur le disque, donc un seul agent à la fois peut y toucher sans risque. Mais alors, comment faire tourner plusieurs agents en parallèle sur le même projet, sans jouer aux chaises musicales avec les branches ?

La réponse tient dans un outil Git déjà présent mais souvent ignoré : le worktree. Un worktree, c'est une deuxième copie de travail du même dépôt, posée dans un autre dossier, mais qui partage le même historique Git : ce n'est pas un clone complet, juste une branche à part entière qu'on peut modifier sans toucher à la branche principale. Claude Code s'appuie directement dessus : le flag --worktree (ou -w) crée ce dossier isolé sous .claude/worktrees/<nom>/, sur une nouvelle branche nommée worktree-<nom>, si bien qu'un agent lancé dedans ne peut tout simplement pas écraser ce que fait un autre agent ailleurs. Reste une question : ce nouveau chantier part d'où ? Par défaut, il part d'origin/<branche par défaut> (une base propre et à jour), mais si vous avez déjà du travail local non poussé que vous voulez prolonger, il faut activer explicitement l'option qui part de votre HEAD local à la place.

Le deuxième point de friction du vibe-coding, c'est la fin de la tâche : une fois le code écrit, il faut encore committer, pousser, ouvrir une pull request (une demande de fusion vers la branche principale, généralement relue avant d'être acceptée). Et c'est précisément là qu'on saute une étape, ou qu'on pousse directement sur la branche principale par réflexe. Claude Code automatise cette mécanique : un agent qui travaille en arrière-plan dans un worktree committe et pousse son travail avant de terminer, et n'ouvre une pull request en brouillon que lorsque la tâche le justifie, en respectant au passage les instructions Git que vous avez laissées dans votre CLAUDE.md. Mais automatiser ne veut pas dire tout laisser faire sans regard : dans ce workflow de commit, push et pull request, les flags qui pourraient faire des dégâts difficiles à rattraper (un push forcé, un commit amendé, un hook de vérification contourné) ne sont plus exécutés automatiquement, ils redemandent une confirmation explicite. Autrement dit, l'automatisation vous retire la corvée répétitive, pas votre dernier mot sur les actions risquées.

Un dernier détail change beaucoup au quotidien : tous les worktrees d'un même dépôt partagent la même configuration (CLAUDE.md, réglages de permissions, agents personnalisés, skills, mémoire automatique), donc pas besoin de tout redupliquer à chaque nouveau chantier parallèle. Et pour garder une vue d'ensemble sans rouvrir GitHub à chaque fois, l'état de la pull request associée à votre branche courante s'affiche sous forme d'un simple point coloré dans l'interface. Voici, en détail, ce que ça change concrètement.

Le flag --worktree (ou -w) crée un worktree isolé sous .claude/worktrees/<nom>/, sur une nouvelle branche worktree-<nom>.

Comment faire

v2.1.133Confirmé

worktree.baseRef vaut "fresh" par défaut (part de origin/<branche par défaut>) ou "head" (part de votre HEAD local, commits non poussés inclus).

Comment faire
{ "worktree": { "baseRef": "head" } } si vous voulez que chaque nouveau worktree parte de votre travail local en cours.

Exercice pratique

Lancez la commande suivante pour démarrer une session isolée :

claude --worktree essai-pro

Modifiez un fichier, puis lancez /code-review high --fix avant de committer, et enfin /commit-push-pr. Vérifiez qu'un git push --force ne serait pas auto‑approuvé, et ajoutez worktree.baseRef: "head" dans .claude/settings.json.

Solution & vérification

claude --worktree essai-pro crée un worktree isolé sous .claude/worktrees/essai-pro/, sur une nouvelle branche worktree-essai-pro, ce qui permet de modifier un fichier sans toucher la branche de travail courante. Une fois le fichier committé, /commit-push-pr pousse le travail et ouvre la PR. Depuis la v2.1.229, il ne s'exécute plus silencieusement pour un flag dangereux : un git push --force redemande confirmation au lieu d'être auto-approuvé. Pour que ce worktree (et les suivants) démarrent depuis le HEAD local, commits non poussés compris, plutôt que depuis origin/<branche par défaut>, il faut ajouter explicitement la configuration suivante dans .claude/settings.json :

{
  "worktree": { "baseRef": "head" }
}

C'est le réglage final attendu par l'exercice.

  • Le répertoire .claude/worktrees/essai-pro/ existe et, à l'intérieur, git branch --show-current renvoie worktree-essai-pro.
  • En tentant un git push --force dans ce worktree via /commit-push-pr, une invite de confirmation explicite apparaît au lieu d'un push exécuté directement.
  • .claude/settings.json contient la clé "worktree": { "baseRef": "head" } après l'édition, et un nouveau worktree créé ensuite a le même commit de tête que la branche locale courante (et non celui d'origin/<branche par défaut>).
