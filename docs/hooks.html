Hooks : automatiser sans dépendre du modèle

Des règles déterministes, pas des espoirs

En vibe‑coding, on laisse le modèle décider seul quand formatter, tester ou demander une confirmation, et il oublie parfois. Les hooks transforment ces habitudes en règles qui s'exécutent toujours au bon moment, scriptables et partageables en équipe.

Et si les bonnes pratiques s'exécutaient toutes seules, sans que vous ayez à les redemander ?

En vibe-coding, on a tous vécu ça : on demande à Claude de lancer les tests avant de committer, ou de formatter le code proprement. Neuf fois sur dix il le fait. Puis un jour il l'oublie, pressé de répondre à autre chose. Rien d'anormal : à chaque étape, le modèle décide lui-même quoi faire, et une décision, même bonne dans l'immense majorité des cas, reste une décision, pas une garantie. Un hook change complètement la donne : c'est une règle que vous écrivez une fois, et qui s'exécute automatiquement à chaque fois qu'un événement précis se produit dans la session, que le modèle y pense ou non.

Concrètement, comment ça fonctionne ? Un hook s'accroche à un événement du cycle de vie de Claude Code (juste avant qu'un outil s'exécute, juste après, avant une compaction du contexte qui résume la conversation pour libérer de la place, et bien d'autres) et déclenche à ce moment précis une action que vous définissez : lancer un script local (type: "command"), appeler directement un outil MCP déjà installé en interpolant les champs de l'événement (type: "mcp_tool"), ou envoyer le JSON de l'événement en POST vers un service externe et attendre sa réponse (type: "http"). Vous pouvez même cibler très finement quand le hook se déclenche, grâce à un champ if qui reprend la syntaxe des règles de permission, par exemple ne réagir qu'aux commandes git avec quelque chose comme Bash(git *). Le hook ne demande rien au modèle : il s'exécute, point final, ce qui en fait un filet de sécurité déterministe plutôt qu'un espoir.

Mais un hook n'est pas forcément une barrière qui arrête tout net. C'est là que ça devient intéressant : sur un hook PostToolUse (celui qui se déclenche juste après qu'un outil a été utilisé), l'option continueOnBlock: true permet de renvoyer la raison d'un blocage à Claude comme un simple résultat d'outil, au lieu d'interrompre brutalement le tour. Un typecheck qui échoue, par exemple, peut ainsi être corrigé automatiquement par Claude dans la foulée, sans que vous ayez à relancer quoi que ce soit vous-même. À l'autre bout de la session, un hook PreCompact peut lui carrément empêcher une compaction de se produire (en renvoyant un code de sortie 2), le temps d'archiver ce qui compte avant que l'historique ne soit résumé.

Et parce que ces règles peuvent vivre dans un fichier de configuration partagé par toute l'équipe, ou même être limitées au cycle de vie d'un skill ou d'un agent particulier via son frontmatter, tout le monde travaille avec les mêmes garde-fous, sans avoir à répéter les mêmes consignes à chaque session. Voici, en détail, ce que ça change concrètement.

✓ Exact. PreCompact se déclenche juste avant une compaction et peut la bloquer (code de sortie 2). PostCompact, lui, se déclenche seulement juste après, ce qui est utile par exemple pour archiver des informations importantes avant qu'elles ne soient compactées.

Quiz éclair

Quel type de hook permet d'appeler directement un outil MCP déjà installé, avec interpolation des champs de l'entrée JSON du hook ?

✓ Exact. Le type mcp_tool appelle directement un outil MCP déjà installé, avec interpolation des champs de l'entrée JSON du hook. C'est utile par exemple pour déléguer une vérification de sécurité à un outil MCP existant, sans réécrire de script shell.
✗ Pas tout à fait. C'est le type mcp_tool : il permet d'appeler directement un outil MCP déjà installé, en interpolant les champs de l'entrée JSON du hook, plutôt que d'exécuter un script (command) ou d'envoyer une requête réseau (http).
Exercice pratique

Créez un hook PreToolUse sur Bash avec if: "Bash(rm *)" qui bloque (code de sortie 2) toute commande rm. Ajoutez un hook PostToolUse sur Edit|Write avec continueOnBlock: true qui lance un linter et renvoie l'erreur à Claude au lieu d'arrêter le tour. Inspectez /hooks pour voir la provenance de chaque hook actif.

Solution & vérification

Le premier hook s'appuie sur le champ if, qui accepte la syntaxe des règles de permission (par exemple Bash(git *)) pour cibler finement une sous-commande. Avec if: "Bash(rm *)", le hook PreToolUse ne se déclenche que sur les commandes rm, et un script qui se termine en code de sortie 2 bloque l'appel d'outil. Le second hook exploite l'option continueOnBlock: true sur PostToolUse, qui renvoie la raison du blocage à Claude comme résultat d'outil au lieu d'arrêter le tour. Un linter en échec peut ainsi être corrigé automatiquement par Claude plutôt que d'interrompre la session. Le réglage final attendu est donc deux entrées dans la configuration des hooks : une sur PreToolUse (matcher Bash, if: "Bash(rm *)", commande qui sort en code 2) et une sur PostToolUse (matcher Edit|Write, continueOnBlock: true, commande qui lance le linter).

  • Une commande rm tentée par Claude est immédiatement refusée : l'outil Bash ne s'exécute pas et le message d'erreur renvoyé par le hook (code de sortie 2) apparaît comme résultat d'outil dans la conversation.
  • Après une modification via Edit ou Write qui casse le linter, le tour ne s'arrête pas : l'erreur du linter apparaît comme résultat d'outil et Claude propose une correction dans le message suivant, au lieu que la session s'interrompe.
  • La commande /hooks liste bien les deux hooks comme actifs, avec leur provenance (le fichier de settings où ils sont déclarés) et leurs matchers respectifs : Bash pour le hook PreToolUse, Edit|Write pour le hook PostToolUse.
