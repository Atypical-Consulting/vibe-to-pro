Checkpoints & Rewind : le filet de sécurité

Explorer sans crainte

Le vibe‑coding enchaîne des prompts à l'aveugle sans filet si Claude part dans la mauvaise direction. Les checkpoints transforment cette improvisation en pratique pro : chaque prompt devient un point restaurable, code et/ou conversation, avant même un commit Git.

Test de niveau

Depuis la v2.1.216, quels fichiers /rewind ignore‑t‑il lors d'une restauration de code ?

✓ Exact. Ces fichiers gardent leur contenu actuel, avec un message « Restored the code, but skipped N files ». C'est utile à savoir pour les dotfiles liés symboliquement.
→ Vous maîtrisez déjà ce levier, passer au module suivant
✗ Pas tout à fait. Ce sont les liens symboliques et liens physiques (hard links) qui sont ignorés, pas les fichiers .env ou binaires.

Et si un prompt raté ne vous coûtait qu'un aller-retour ?

Vous connaissez sans doute déjà cette sensation en vibe-coding : vous enchaînez les prompts, Claude touche deux ou trois fichiers à chaque fois, et à un moment donné une demande part dans la mauvaise direction. Le réflexe naturel, c'est de rattraper le coup à la main, prompt après prompt, en espérant revenir à peu près à l'état d'avant. C'est justement le problème que les checkpoints (des points de restauration, un par étape) viennent résoudre : chaque prompt que vous envoyez devient automatiquement un point auquel vous pouvez revenir, sans avoir eu besoin de faire un commit Git au préalable pour vous protéger.

Concrètement, comment ça marche ? Vous appuyez deux fois sur Échap, ou vous tapez /rewind, et un menu s'ouvre avec la liste de ces points : un par prompt envoyé, dans l'ordre. Vous pouvez aussi aller droit au but en passant un argument direct (un numéro de tour comme dans /rewind 5, un nom de checkpoint ou une description) plutôt que de parcourir la liste. L'idée derrière ce découpage par prompt, et non par simple sauvegarde de fichier, c'est que l'unité de travail en vibe-coding, c'est l'échange : une demande, une réponse de Claude, des fichiers modifiés en conséquence. Revenir à « juste avant ce prompt » correspond donc exactement à la façon dont vous pensez votre erreur.

Mais que restaure-t-on au juste quand on choisit un point ? Là encore, le mécanisme est pensé pour coller à votre besoin réel : vous pouvez restaurer le code et la conversation ensemble, pour effacer à la fois les fichiers modifiés et la trace de la mauvaise demande, ou restaurer le code seul, en laissant la conversation garder le souvenir de ce qui s'est passé. C'est utile si vous voulez comprendre après coup pourquoi Claude est parti dans cette direction. Une troisième option, « Summarize up to here », répond à un besoin différent : elle compresse l'historique de conversation avant le point choisi, sans toucher aux fichiers sur le disque. Ce n'est donc pas un outil pour rattraper une erreur, mais pour libérer de la place dans une conversation qui s'est trop allongée, sans perdre le travail de code déjà fait.

Un point de vigilance tout de même : cette restauration du code n'est pas totalement aveugle. Les liens symboliques et les liens physiques (des fichiers qui pointent vers un autre fichier plutôt que de contenir leurs propres données) sont volontairement ignorés lors d'une restauration : ils gardent leur contenu actuel, et Claude Code vous prévient explicitement par un message plutôt que de les modifier en silence. Et si le filet de sécurité ne se limite pas au code d'une session en cours, il existe aussi un réflexe complémentaire pour la continuité entre sessions : --continue reprend directement la conversation la plus récente du répertoire courant, tandis que --resume ouvre un sélecteur ou cible une session précise par son identifiant. Voici, en détail, ce que ça change concrètement.

Quiz éclair

Quelle est la différence entre --continue (-c) et --resume (-r) ?

✓ Exact. Exact. --continue (-c) reprend directement la conversation la plus récente du répertoire courant, sans choix à faire, tandis que --resume (-r) ouvre un sélecteur de sessions ou reprend un ID de session précis que vous lui indiquez.
✗ Pas tout à fait. Pas tout à fait. Les deux options ne sont pas interchangeables : --continue reprend automatiquement la dernière conversation du répertoire courant, --resume ouvre un sélecteur ou cible une session par son ID.
Exercice pratique

Faites implémenter une fonctionnalité simple, laissez Claude modifier 2‑3 fichiers, puis demandez volontairement une modification que vous jugez mauvaise. Appuyez deux fois sur Échap (ou /rewind), choisissez le point juste avant, testez « Restore code and conversation » puis, sur un autre essai, « Restore code » seul.

Solution & vérification

Appuyer deux fois sur Échap (ou taper /rewind) ouvre le menu de checkpoints, qui liste un point restaurable par prompt envoyé, comme le décrit le fait sur /rewind (v2.0.0). Cela permet de repérer sans ambiguïté le tour juste avant la modification jugée mauvaise, plutôt que de compter des commits Git. En choisissant « Restore code and conversation » sur ce point, le code des 2‑3 fichiers modifiés et l'historique de conversation reviennent tous deux à cet état ; en refaisant l'essai avec « Restore code » seul, seuls les fichiers sur disque sont restaurés, la conversation gardant elle la trace de la demande jugée mauvaise. La manipulation attendue se résume donc à /rewind (ou Échap x2), puis sélection du checkpoint immédiatement antérieur à la mauvaise demande, testé une fois avec chaque option de restauration.

  • Avec « Restore code and conversation » : le prompt jugé mauvais et la réponse de Claude qui a suivi disparaissent visiblement du fil de conversation affiché, et le contenu des 2‑3 fichiers modifiés correspond à leur état d'avant ce prompt (vérifiable en les rouvrant ou via un diff).
  • Avec « Restore code » seul : le contenu des fichiers revient au même état d'avant le prompt, mais le fil de conversation continue d'afficher intégralement le prompt jugé mauvais et la réponse de Claude. C'est ce contraste qui prouve que seule la restauration du code a eu lieu.
  • Aucun message du type « Restored the code, but skipped N files » n'apparaît pour ces fichiers ordinaires ; un tel message ne doit surgir que si l'un des 2‑3 fichiers concernés est un lien symbolique ou physique.
